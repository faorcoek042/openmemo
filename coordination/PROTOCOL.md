# Agent 协作协议 v1

所有 agent **必须**遵守。Meta Manager 是唯一的调度者与合并者。

## 0. 角色

- **Meta Manager**（主会话）：分派任务、读摘要、做决策、写 ADR、合并成果。不写业务代码。
- **Lead Agent**（opus5）：领域负责人，可再派 sub-subagent（琐碎活用 sonnet5）。
- **Worker Agent**（sonnet5）：执行明确定义的机械任务。

## 1. 通讯机制 = 共享文件系统（单一事实来源）

```
/root/memo/
├── docs/
│   ├── 00-CHARTER.md          # 项目章程（Manager 所有，只读）
│   ├── research/              # 研究报告  R-*.md
│   ├── design/                # 设计文档  D-*.md
│   └── adr/                   # 架构决策记录 ADR-NNN-*.md（仅 Manager 写）
├── coordination/
│   ├── PROTOCOL.md            # 本文件
│   ├── BOARD.md               # 任务看板（仅 Manager 写）
│   ├── ROSTER.md              # Agent 花名册（仅 Manager 写）
│   ├── inbox/<agent>.md       # Agent → Manager 的回执（Agent 写，追加）
│   └── tasks/T-NNN.md         # 任务卡（Manager 写规格，Agent 写进展）
```

### 规则

1. **写自己的文件，读别人的文件。** 除 `inbox/<自己>.md`、自己被分配的 `tasks/T-NNN.md`
   和自己交付的 `docs/**` 文件外，不得修改任何文件。避免写冲突。
2. **跨 agent 依赖靠文件，不靠猜。** 需要别人的产出时，读对方的 `docs/` 交付物。
   若尚不存在，在自己的 inbox 里写 `BLOCKED: 等待 <文件路径>`，然后先做不依赖它的部分。
3. **绝不修改他人的交付物。** 有异议 → 在自己 inbox 里写 `DISPUTE:` 条目，Manager 裁决。

## 2. 交付物格式（强制）

每份 `docs/**` 文档**必须**以这个块开头，Manager 只读这一块：

```markdown
---
id: R-01
author: <agent-name>
status: draft | ready | superseded
date: YYYY-MM-DD
---

## TL;DR（≤ 25 行，Manager 只读这里）

- 结论 1
- 结论 2
- 关键取舍：...
- 未验证/存疑：... <-- 必填，没有就写"无"
- 对其他 agent 的影响：...

## 详细内容

（正文随意长）
```

## 3. 回执格式（`coordination/inbox/<agent>.md`，追加不覆盖）

```markdown
## [YYYY-MM-DD HH:MM] <TASK-ID> <STATUS>

STATUS ∈ DONE | PROGRESS | BLOCKED | DISPUTE | QUESTION
交付: <文件路径列表>
要点: <≤5 行>
下一步建议: <≤3 行>
需要 Manager 决策: <有则列出，无则写"无">
```

## 4. 诚实规则（不可协商）

- 没验证过的写 **"未验证"**。没跑通的写 **"未跑通"** 并附错误输出。
- 不允许编造 API、版本号、benchmark 数字。不确定就去查，查不到就标 `UNKNOWN`。
- 网络受限导致无法验证的，明确写 `无法联网验证`。

## 5. 派生 subagent 的规则

- Lead 可派 sub-subagent，但**自己名下同时运行的不得超过 2 个**（全局上限 4 由 Manager 控制）。
- 机械性工作（改文件名、批量重写、跑格式化、写样板代码）→ 用 sonnet5。
- 需要判断/设计/取舍的 → opus5。
- 派出去的 agent 完成后不要 kill，记录其 name/id 到自己的 inbox 以便复用。

## 6. 上下文节约

- 不要把大文件全文贴进回复。写到磁盘，回复里只给路径 + TL;DR。
- 读别人的文档时优先只读 TL;DR 块。

## 7. 共享产物：`apps/web/dist` 不许被验证构建覆盖

`:10000` 的演示实例（用户唯一能从 NAT 外访问的入口）**直接托管 `apps/web/dist`**。
任何 agent 跑一次 `vite build`，都会**换掉用户正在看的前端** —— 进程没重启、
版本号没变、页面却已经是别人的半成品了。没有任何东西会报错。

所以：

- **验证构建一律 `--outDir` 到 `/tmp/<你的名字>/`**，例如
  `vite build --outDir /tmp/llm-picker/dist`。
- `apps/web/dist` **只由 Manager 在重启前统一构建**。
- 不确定某条命令会不会写进去，就先 `--outDir` 到 `/tmp`。

同理适用于 `:10000` 本身：**只读，不重启、不 kill、不占用该端口**。要起服务用别的端口。

（此规则源于 `llm-picker` 的主动申报 —— 它构建完才意识到，并如实报了出来。
规则针对的是"没人知道这条线存在"，不是针对它。）

## 8. 断言 DOM 节点不许直接比对象 —— 会 OOM，而且假装成"测试挂了"

`assert.equal(domNode, null)` **失败时**，node:test 要为两边算 diff，`util.inspect` 会顺着
`parentNode` / React fiber **展开整棵树**。实测进程涨到 **10.5 GB**，表现是：

- 不是"断言变红"，而是**整个测试文件炸掉**（57 秒后 `'test failed'`，同文件里其它 suite 一个没跑）
- **同进程里别人的用例统计一起被带偏**

**比"护栏没变红"更难查** —— 因为它看起来像环境问题、像超时、像别的 agent 把仓库弄坏了，
而不像"我这条断言写错了"。

所以：**断言 DOM 存在性一律先转成布尔或字符串再比**。

```js
assert.equal(el === null, true); // ✅
assert.equal(!!container.querySelector(sel), false); // ✅
assert.equal(el, null); // ✘ 失败时 OOM
```

同理适用于任何**可能持有父引用的对象**（DOM 节点、fiber、带 `parent` 指针的树节点、
含循环引用的图）。判据不是"它是不是 DOM"，是"**它失败时会被 inspect 展开多大**"。

（源于 `models-page-fix` 的反向验证 —— 它第一次没拿到红灯，追下去才发现是 OOM，
并如实报了出来而不是重跑一次糊弄过去。）

### §7 补充：用 `pnpm build:safe`，不要靠记性

§7 禁止验证构建覆盖 `apps/web/dist`，但**两名 agent 先后踩了同一个坑**，成因是同一个：
HANDOFF 教的启动步骤就是 `pnpm -r build`，而禁令针对的是它的**子步骤**（`vite build`）——
两句话隔了几十行，**读到禁令的人不会意识到自己刚敲的那条命令就违反了它**。

所以禁令改成脚本：

```bash
pnpm build:safe     # ✅ 构建除 web 之外的全部包，不会碰 apps/web/dist
pnpm -r build       # ⚠️ 含 vite build，只有 Manager 在重启前跑
```

**判据不是"要记得别跑那条命令"，是"跑错了也不会造成后果"。**
一条需要人时刻记住的规则，等价于一条迟早会被违反的规则 —— 这次是两次。

（源于 `ytdlp-install` 的自我申报：它违反后没有掩盖，而是分析出"两句话隔了 60 行"
这个真正的成因并建议加脚本。）

## 9. 数据目录指针是**全局单例**，测试搬迁绝不能碰它

指针文件在 `~/.local/share/openmemo/datadir.json`，**按设计就在数据目录之外**
（鸡生蛋：数据搬走后得先知道搬到哪了，指针跟着走就再也找不到了）。

代价是：**它是全机器共享的一份**。任何 agent 跑一次会写指针的搬迁流程，
就把**用户的 demo 一起搬走了** —— 而且不会立刻显形，要等下一次重启。

已经发生过一次：某轮测试把它改成了 `/tmp/<agent>/movedst`，
Manager 几小时后重启 demo，daemon 挂到一个空壳上 ——
**用户的 DeepSeek key、模型、转写记录全部"消失"**，自检从 `ok:20 fail:0` 掉到 `ok:7 fail:5`。
数据一个字节没丢，但从界面上完全看不出这一点。

所以：

- **测搬迁只调纯函数**，不走会写指针的那条路径；
- ~~非走不可就**先备份指针、跑完还原、并核对内容**~~ → **见 §9-bis：备份还原法已作废**；
- Manager 重启前**先确认 `dataDir` 是不是用户那个**。

**判据：一个进程级测试写了机器级状态，就已经越界了 —— 哪怕它自己的临时目录用得很干净。**

### §9-bis 那次事故有**第二条路径**，而它藏在最常跑的那条命令里

上面这条规则只说了"**测搬迁**别碰指针"。**它漏掉了 `pnpm -r test` 本身。**

`apps/daemon/src/storage/restart-datadir.test.ts` 要验的性质是
「指针指向别处时，普通重启的 dataDir 不能被带偏」——
它**必须**让 daemon 真读到一个指向别处的指针。它当时的做法**恰好就是上面那条被允许的兜底**：
备份 → 写诱饵 → `after()` 还原。还原写得对，内容也确实还原得回来。

问题是：**`after()` 只在正常结束时跑。**

进程被 `kill`、崩溃、超时、机器重启 —— 指针就**永久**停在 `/tmp/om-rd-decoy-*` 上。
而 `pnpm -r test` 是一天要跑十几次的命令。事故当时归因于"某个 agent 的搬迁测试"，
**这条路径一直开着，谁都没看见**。

`[实测]` 把当时那段备份/还原逻辑逐行搬到假 HOME 下跑，中途 `kill -9`：

```
--- ① 正常跑完（after() 有机会跑）
{ "dataDir": "/root/data-memo", ... }          ← 还原成功
--- ② 跑到一半 kill -9（after() 没跑）
{"dataDir":"/tmp/om-rd-decoy-XXXX"}            ← 用户的 demo 已经废了
```

所以规则改成：

- **判据不是"还原得对不对"，是"被 kill 也不能留下坏状态"。**
  任何"写下去 → 再改回来"的方案都在结构上满足不了它 —— 写与还原之间必然有窗口。
- **正确的修法是让它根本不写那个全局位置。**
  指针位置已经可以被 `OPENMEMO_POINTER_FILE` 覆盖（与 `OPENMEMO_DATA_DIR` /
  `OPENMEMO_EXT_DIR` / `OPENMEMO_MODELS` 同一套约定）。测试在**模块顶层**设它，
  窗口为零；node:test 一个测试文件一个子进程，进程一退它就没了，**不需要清理代码**
  —— 而"清理代码"正是上面那个靠不住的东西。
- **覆盖要有人守。** 该测试里有一组用例专门断言
  「本次要写的指针路径必须在 tmpdir 里、且不在 `$HOME` 底下」+
  「`pointerFile()` 回读必须等于我们设的那个」。
  重定向被"顺手简化"掉时会当场红 —— 而不是等用户的 demo 挂了才知道。

**推广到一般情形（这条才是要记住的）：**

> 判断一个测试有没有越界，看的不是"它清理得干不干净"，
> 而是**"把它 `kill -9` 在最坏的那一行上，机器会留下什么"**。
> 留下任何机器级的坏状态 —— 就得改成"根本不写"，而不是"写完记得擦"。

同类需要用这条判据重新审一遍的（**尚未逐个核查**）：全局配置文件、
`~/.config` / `~/.cache` 下的任何路径、系统级临时文件的固定名字、端口占用、
以及任何 `process.env` 之外的进程间共享状态。

**推论：变异检查这类"故意把安全性质拿掉"的工具，必须假设变异体是敌对的。**
`scripts/mutation-check.mjs` 第一版就栽在这上面 —— 它有一条变异是
"让 `pointerFile()` 忽略覆盖、改回硬编码全局位置"，跑完**它自己把用户的指针写坏了**：
一个用来防止事故的工具，复现了那场事故。现在每个变异体都跑在假 `HOME` / `XDG_DATA_HOME` 里。

## 10. 反向验证不许在共享工作树里做

反向验证要求"把修复拆掉、确认真的变红"。问题是：**拆掉的那几分钟，`dist` 里装着故意坏掉的代码**，
而别的 agent 同时在跑 `pnpm -r test`。

已经发生：某轮六组反向验证期间，另一路 agent 撞上 25 条红，逐个排查后确认「不是我的」——
**而拆修复那一方每次都还原了、`grep` 残留一直是 0。**

> **「最终状态干净」救不了「过程中别人跑了一次」。**

判据与 §9-bis 是同一条的两面：

- §9-bis 问的是 **「在最坏的那一行 kill -9，机器上还剩下什么」**
- 这一条问的是 **「在最坏的那一秒，别人看到的是什么」**

所以：

- **反向验证跑在 `/tmp` 的隔离副本上**（`scripts/mutation-check.mjs` 已经是这个形状，照它做）；
- 非在共享树里不可时，**先在 inbox 申报时间窗**，并在完成后主动说一声；
- 撞上红灯的一方，**先看 inbox 有没有人正在做反向验证**，再判断是不是自己的。

**推论：一个"必填字段"类的改动，在补齐所有构造点之前，红是必然的，不是意外。**
这类改动要么一次提交到位，要么申报窗口。

（源于 `catalog-truth` 的主动认领与成因分析 —— 它没有说"最后是绿的"，
而是指出中间态被别人看见了。）

## 11. 残留进程会把「本该失败」变成「假通过」—— 而且是静默的

**本轮三个 agent 各撞了一次同一个形状**，所以它进协议：

- `bundle-launch`：一条诊断步骤把 daemon 起了起来并**泄漏**，占着 17650。
  于是「`open` 一个被 Gatekeeper 拒绝的 `.command`」这一步**报出界面可达 HTTP 200** ——
  而那个 200 是**泄漏进程**应答的，`open` 自己是 ETIMEDOUT。
  **差一点就据此报告「macOS 双击是好的」，而用户手里的包明明打不开。**
- `e2e-import`：健康检查连上了同端口的一个游离 daemon，**0.5 秒就报「就绪」**，
  而它自己拉起的那个已经死了。
- `e2e-record`：跳过的平台报告**「成功，零步骤」**。

**为什么它比测试失败危险得多**：失败会被查，**假通过不会**。
它还会**反向**污染结论 —— 你会去修一个不存在的问题，或者宣布一个坏掉的东西是好的。

与 §9-bis / §10 是同一族的第三面：

|         | 问的是                                                         |
| ------- | -------------------------------------------------------------- |
| §9-bis  | 在最坏的那一行 `kill -9`，**机器上还剩下什么？**               |
| §10     | 在最坏的那一秒，**别人看到的是什么？**                         |
| **§11** | 我这次测到的「通过」，**会不会根本不是我启动的那个东西给的？** |

所以：

- **任何「起服务再探测」的测试，探测前必须先证明那个端口是空的**，
  并在不空时**当场判失败**（而不是继续跑下去拿一个无意义的绿）。
- **收尾按 pid 收整棵进程树**（Windows 上 `child.kill()` 杀不掉 `cmd.exe` 底下的 `node.exe`；
  POSIX 上 `exec` 之后才是同一个 pid）。**仍然按 pid，不许 `pkill -f`** ——
  模式匹配会打到别人的进程，那是另一种越界。
- **一切外部命令带超时。** 没有超时的步骤既会拖死整条腿，
  又会在被杀时把孙子进程留下来 —— 上面两个后果它一个人全占。
- **「跳过」不许渲染成「成功」。** 零步骤的绿灯是本条最廉价的一种发作。

**判据**：一个绿灯，必须能追溯到**是我这次启动的那个东西**给的。**追溯不到，它就不是证据。**

> Manager 注（2026-08-08）：本条由 `bundle-launch` 起草，我收进来时只加了 `e2e-record`
> 那一例与「跳过不许渲染成成功」一条 —— 那是同一个形状最便宜的发作方式，
> 而它已经真的发生了。

## 12. `git diff --cached` 只在你检查的那一瞬间为真

**索引是所有 agent 共享的一份机器级状态。** 本条由 `e2e-record` 用一次真实事故换来:

> 他做了当时纪律要求的每一步 —— 逐 hunk `git apply --cached`、提交前核对 `git diff --cached --name-only`
> 干净 —— **然后在核对与 `git commit` 之间,另一位提交了,索引被重置。**
> 结果那次提交**丢了他自己的工作,还夹带了对方两个 hunk**。

**所以"逐文件 stage + 提交前核对全量 `--cached` 列表"是不够的。** 它防的是"我 add 多了",
防不住"**在我这两条命令之间,世界变了**"。这是 §11 的同族:**一个在检查那一刻为真的结论,
不等于在你据此行动那一刻仍然为真。**

规则:

- ⚠️ **`git commit -- <pathspec>` 对「未跟踪的新文件」是静默 no-op** —— pathspec 只从
  已跟踪内容里挑,新文件**根本进不去**,而命令**照样 exit 0**。
  新文件必须先 `git add <path>`(**只 add 自己的**),再 `git commit -- <pathspec>`。
  `[实测]` `docs-sync` 撞到过:第一次提交静默漏掉新文件,**而且另一位恰好在那个窗口里提交了** ——
  是下面那条「提交后复核」把它暴露出来的。**这一条是本款自己的洞,由踩到的人补上。**
- **用 `git commit -- <pathspec>` 提交**,而不是"先 stage 再 commit"。
  pathspec 让"提交哪些文件"和"提交"成为**同一个动作**,中间没有可以被别人插进来的窗口。
  ⚠️ **不带 pathspec 的 `git commit` 会带走索引里的一切,包括别人刚 `git add` 的东西。**
  `[e2e-browser 实测]` 他先 `git status` 确认只有自己的 4 个文件,
  接着 `git add <自己的 4 个>` + `git commit`(**没带 pathspec**)——
  提交里多出一个 `scripts/build-bundle.mjs`:**并发 lane 恰好在这两条命令之间把它 add 进了索引**。
  是"提交后 `git show --stat` 复核"当场抓到的。
  善后(**没有 `--amend`**,且当时尚未 push):`git reset --soft HEAD~1`
  → `git restore --staged <别人的文件>` → 改用 `git commit -- <pathspec>` 重提。
  **"我 `git status` 看过了"不构成保护 —— 那正是本款标题说的那一瞬间。**
- **提交之后立刻 `git show --stat` 复核**:文件列表是不是恰好是你要的。
  **不是提交前核对,是提交后核对** —— 只有提交后的那份是既成事实。
- **撞到夹带时不许 revert 对方的 hunk** —— 那会把别人的工作从 master 上删掉。
  正确做法是:保住自己的、**在回执里声明对方的作者身份落在了你的提交里**,并告知 Manager。
- 工作区有别人在途改动时,**门禁跑在隔离 worktree 检出你自己那个 commit 的树上**。
  ⚠️ 共享 `node_modules` 里的 `@openmemo/*` 软链**会把别人未提交的改动漏进你的隔离环境**
  （`e2e-record` 实测撞到过）—— 需要把那些链接重新指到你自己的树。
- 🆕 **提交前跑 `pnpm format:changed <路径…>` —— ⚠️ 必须带路径。**

  **两种模式，用错时机等于什么都没查：**

  | 什么时候           | 怎么跑                                                   | 它查的是                                                |
  | ------------------ | -------------------------------------------------------- | ------------------------------------------------------- |
  | **提交前**（自检） | `pnpm format:changed <照抄 `git commit -- ` 后面那一串>` | **你即将提交的那几个文件**（工作树里的内容）            |
  | **推送前**（复核） | `pnpm format:changed`（无参数）                          | `origin/master..HEAD` —— **已经提交、即将 push** 的内容 |

  ⚠️⚠️ **提交前跑无参数模式 = 什么都没查。**
  你还没提交，`origin/master..HEAD` 里当然没有你那几个文件 ——
  它会诚实地打印「**没有检查任何东西（这不是"通过"）**」，
  **但那行字很容易被当成"没东西要查 ⇒ 没问题"扫过去。**

  `[真事，2026-08-10]` **Manager 向至少八个 agent 广播了「提交前跑 `pnpm format:changed`」**
  ——**漏了"带路径"这三个字**。于是一群人跑了一个**结构上查不到任何东西**的检查，
  然后以为查过了；这很可能就是 `Format check` 反复变红的原因之一。
  ⚠️ **发现它的不是任何一条纪律，是工具自己那句诚实输出**：`a534e2e5…` 照着广播跑，
  看到「没有检查任何东西」，**没有把它当成通过**，改成提交前 `prettier --check <文件>`、
  提交后再用无参数模式复核。**"我按指令做了"不等于"我查到了东西"。**

  ⚠️ **参数照抄 `git commit -- ` 后面那一串** —— 让"检查的范围"和"提交的范围"
  是**同一份文本**，它们就不可能漂移（这是 §15 那条判据正着用）。
  ⚠️ **它不替代 `pnpm format:check`**：它只看你点名的文件，
  **"漏掉别人漏的"是它的设计，不是缺陷** —— 全仓那一档是 CI 的 `Format check` job。
  为什么需要它：`format:check` 挂在 `pnpm check` 里，而后者含 `build:safe`（几分钟），
  于是**没有人跑它**。`[实测 2026-08-10]` `Format check` 连红五次、**四个不同作者**，
  其中一次是在别人正清理前一批的**那二十分钟里**落地的 —— **不是谁不小心，是没有拦截点**。
  ⚠️ **口径不许换成 `git diff --name-only HEAD`**（工作树 vs HEAD）：
  那在共享树上会列出**所有人**未提交的改动，照它去格式化就是动别人没写完的文件 ——
  与 §15/§15-ter 同一族（**作用域比使用者以为的宽**）。

**判据**:你据以行动的那个事实,必须在**行动的那一刻**仍然成立;做不到就把检查和行动合并成一个动作。

## 13. 裁完之后回去改原文，是一个会被静默跳过的步骤

**本轮四次同形**,所以它进协议:

| 原文                                            | 实际状态                                                                     | 烂了多久           |
| ----------------------------------------------- | ---------------------------------------------------------------------------- | ------------------ |
| `ADR-003` 决策 4:daemon 会清 macOS quarantine   | 全仓零 `xattr`;**有人早就发现了,只在 workflow 里挂了个 ⚠️,ADR 原文一字未动** | 约半个月           |
| `ADR-002:24`:`@blocknote/xl-*` (GPL-3.0) ✅允许 | 该包**从未被采用**,而这行留着等于给未来的人一张引入 GPL 的通行证             | 建仓至今           |
| `D-17 §5`:命令行 `tar` 能避开 quarantine        | **实测是错的**,`tar` 和归档实用工具都会传播                                  | 直到被真机实测撞破 |
| `D-03` 的 4 处「请裁决」                        | **`ADR-010` 决策 2 早就裁了**,`D-01` 也订正过,只有 `D-03` 原地不动           | 约 3 个月          |

**共同形状**:结论产生了、也被记在了**某个地方**,但**产生结论的那份原文没有被回去改**。
于是下一个人读到的是旧的那份,**而且它看起来仍然是活的**(还挂着"请裁决"、还写着"✅允许")。

**在别处挂警告不叫修** —— 那只是把不实**搬到了一个更少人读的地方**。

规则:

- **裁决落地 = 改原文 + 记依据,两件一起做完才算完。** 只做后半件的,视为没做。
- **原文用删除线保留,不许删** ——「此前写着什么」是可追溯性的一部分,
  而且能让下一个人看出"这里被改过、为什么改"。
- **写清「何时、被谁、依据什么」**。`ADR-003 §7.6` 与 `D-17 §5.1` 是格式先例。
- **谁发现原文不实,谁就地改** —— 哪怕那份文档不是他的地盘。
  发现的人手里有证据,而"等它的主人来改"就是上面那张表的成因。
  越界要在回执里申报,由 Manager 追认(本轮已有两次先例,都追认了)。
- **`docs/**` 与 `docs/adr/**` 归 Manager** —— 但上一条优先:**宁可越界改对,不要守界烂着。**

**判据**:一份文档里任何"待裁决 / 待办 / 未验证"的标记,都必须**今天仍然为真**。
它为假的时间,就是它在误导人的时间。

## 14. 让人停止追问的那句话，必须自己先被追问一次

有两种句子会让读者**停止核查**。措辞不同，作用完全一样：

> **「这个已经做了。」** 和 **「这条依据 X。」**

一旦写下，下一个人就不会再去看 —— 而且会**在它上面继续加东西**。
所以这两种句子的错误是**复利**的：错得越久，建立在它之上的东西越多。

### 14.1 声称已做，实则零实现

- `runner.ts:190` 声称 Windows 上用 `taskkill` 杀进程树 —— **全仓零实现**。
- `folderById` 声称「由调用方决定 deleted 算不算 404」—— **五个调用方没有一个去检查**。

**可机械化**：这一类的判据是**存在性**，机器查得动（那段代码在不在、那个调用有没有）。
`check-orphan-exports.mjs` 与 `check-contract-fields-shown.mjs`
（"送到前端的字段，界面必须真的读它"）都属这一族 —— **反过来查"声称的东西有没有落地"**。

### 14.2 声称有出处，而出处里根本没有那句话

`[实测 2026-08-09]` `packages/pipeline/src/tools.ts` 的注释写着
「**D-01 §8.4 L2 forbids PATH lookups for real invocations**」。
去读 `D-01 §8.4`：**第二层（L2）是「绝不经过 shell」**（`D-01:1172`），
该节**从头到尾没有禁止过 PATH 查找**。那条禁令是注释**凭空发明、并挂到文档名下的**。

后果不是"多一句错话"：它**把产品立场写反了** —— 用户明确允许
"借系统 ffmpeg、只是优先级低"，而注释按那条杜撰的禁令把它写成了"仅供开发"。

**与 §13 是反向的一对**：

|           | 形状                               | 为什么难查                         |
| --------- | ---------------------------------- | ---------------------------------- |
| §13       | 裁决了，**没回去改原文**           | 原文看起来还活着                   |
| **§14.2** | **原文从来没这么说，是引用者编的** | **带出处的断言看起来已经被审过了** |

**判据：引用即承诺。** 写下「依据 X」的人，有义务确认 X 里真有那句话；
**核不到就不许写出处** —— 宁可写「我们的判断是…」，也不要挂一个不存在的依据。

**机械化只能做到一半，这一点要说清**：

- ✅ **锚点存在性**可查（`D-\d+ §…` / `ADR-\d+ 决策 \d` 指向的文件与章节在不在）；
- ⛔ **"那句话是不是那个意思"查不了** —— 本轮这条的锚点 `§8.4` **是存在的**，
  错的是内容。自动判定需要语义比对，**做成检查必然常态红或大量假阳**，
  而常态红的守卫等于没有守卫。

所以本条**不配套语义检查**，靠的是上面那句判据本身。
⚠️ 将来若要加锚点存在性检查，必须满足：**今天就是绿的**，
且**匹配结构化的引用形式而不是自然语言措辞**
（"靠散文措辞撑着的守卫，是一条会静默停止工作的守卫"）。

## 15. 共享树上禁止 `git stash` —— 它会静默销毁**别人**的工作，尤其是未跟踪的新文件

**这是本树上第一次真正的"工作被别人静默销毁"。** 由 `e2e-browser` 用一次真实事故换来：

> 他手上有 4 个改好、跑绿、**尚未提交**的文件，外加一个**未跟踪**的新测试文件。
> 另一路 rebase 时执行了 `git stash -u`。
> 一瞬间：4 个文件回到 HEAD 状态、新测试文件**从磁盘上消失**，
> 而 `git status` **看起来干干净净**。他是在 `git commit` 报
> `pathspec '…selfTestWrongCard.test.ts' did not match any files` 时才发现的。

**为什么这条比 §12 更狠**：§12 的事故是"我的提交夹带了别人的东西"，**看得见**；
这条是"我的东西没了，而且现场看起来一切正常"。**受害者不会立刻发现** ——
他下一步很可能是"咦，我不是改过吗"，然后**重写一遍**，或者更糟：
以为自己记错了，**把已经修好的缺陷当成没修**。

⚠️ **它咬的正是未跟踪文件,而新测试、新模块最常见的形态就是未跟踪。**
一条刚写完还没 `git add` 的新测试，是这条纪律的典型受害者。

### 规则

- ⛔ **共享工作树上不许 `git stash`**，**尤其不许 `git stash -u` / `-a`**。
  它作用于**整棵树**，不区分谁的改动 —— 你 stash 的是**所有在途 lane** 的未提交工作。
- ⛔ **不许 `git stash pop` / `apply` 别人留下的 stash**：那会把别人的 WIP
  一起吐回工作区，要么覆盖你的、要么撞成冲突。

### 需要一棵干净的树来 rebase 时，照这个顺序做

1. **首选：先把自己的部分提交掉，就没有要 stash 的东西了。**
   §12 的 `git add <只有自己的新文件>` + `git commit -- <pathspec>`。
   **提交是本地的、可撤的、不销毁任何东西**，而 stash 会动别人的磁盘。
   `[本轮实测]` 我第二次提交前就是这么做的：先提交，再 rebase，零风险。
2. **次选：`git rebase --autostash`（不是 `git stash`）。**
   `[隔离 /tmp 仓实测，非听说]` 造出「一个已跟踪改动 + 一个未跟踪新文件」的现场后：
   - `git rebase --autostash <base>` → **未跟踪文件原地不动、已跟踪 WIP 自动回来**；
   - 同一现场 `git stash -u` → **未跟踪文件当场消失**。
     差别的原因：autostash 走的是**不带 `-u`** 的 stash，**未跟踪文件根本不在它的射程内**。
     ⚠️ 但 autostash **仍然会动别人的已跟踪 WIP**（stash 再 apply），
     apply 撞冲突时会把烂摊子留在树上。**所以它是次选，不是首选。**
3. ⚠️ **无论走哪条，新文件写完就 `git add`** —— 哪怕还不提交。
   进了索引的文件即使被卷走也**必定**能从 stash 的索引提交里取回；
   从没进过索引的文件，一旦 stash 被 `drop`，就只剩 `git fsck --lost-found` 那点运气。

### 万一已经被卷走了：只挑自己的路径，**绝不 `pop`**

`[本轮实测有效]`，且**全程没有动那个 stash**（别人的 WIP 原样留在里面）：

```bash
# 0. 先确认没有漂移：stash 的基就是当前 HEAD？不是就要逐个 hunk 看
git rev-parse "stash@{0}^1"; git rev-parse HEAD

# 1. 看清楚 stash 里有什么（^3 是未跟踪那一份，普通 show 看不到）
git stash show --name-only "stash@{0}"
git ls-tree -r --name-only "stash@{0}^3"

# 2. 已跟踪文件：只把**自己的路径**那部分差异捞回来
git diff "stash@{0}^1" "stash@{0}" -- <只写自己的路径> | git apply

# 3. 未跟踪文件：从第三个父提交里单独取
git show "stash@{0}^3:<自己的路径>" > <自己的路径>
```

⚠️ **第 2 步的 pathspec 必须只写自己的文件。** stash 里混着好几路的 WIP，
路径写宽一点就等于替别人 `pop` 了。
⚠️ **不要 `git stash drop`** —— 那个 stash 不是你的。

**判据**：任何会**改动别人磁盘上未提交内容**的命令，在共享树上都是禁止的；
需要干净树时，**用"把自己的提交掉"来换，而不是用"把大家的藏起来"来换**。

### §15-bis 看见一条**陈旧的** stash 挂在那儿，该怎么办

上面那条只说了「别 stash」和「万一被卷走了怎么取自己那部分」。
**它没说：一条已经存在的 stash 该怎么处置。** 而 `git stash pop` 恰恰是最容易被
顺手敲出来的命令 —— 于是那条 stash 会一直挂着，直到有人敲了它。

> ⚠️ **stash 里的东西只会越来越旧，而 `pop` 是"用旧的盖掉新的"。**
> 卷走的那一刻它是当时的最新版；之后受害方多半已经**重做并提交**了 ——
> 你 pop 一下，就把他们更新的版本盖回旧版，而且**不会有任何冲突提示**
> （工作树那时是干净的，apply 会安静地成功）。

规矩三条：

1. **不要 `pop` / `apply` 整条 stash。** 要内容就只读地取**自己那一部分**
   （已跟踪：`git diff stash@{0}^1 stash@{0} -- <只写自己的路径> | git apply`；
   未跟踪：`git show stash@{0}^3:<自己的路径> > <路径>`）。
2. **`drop` 之前必须逐文件证明内容已在 HEAD。**「当时没丢数据」不等于「现在可以扔」——
   前者是关于过去的结论，后者需要**现在**的证据。判据是**内容等价**，不要求逐字
   （受害方多半是重做的，措辞会不一样）。
3. **只要有一处只存在于 stash 里，就停下来报 Manager。** 那不是拆雷，是抢救。
   报之前先把那份内容**另存到 /tmp**，这样"等一下再决定"的代价就是零。

**核对方法（`[实测有效]`，2026-08-10 用在那条 `pre-rebase stash` 上）：**

```bash
# 逐个已跟踪文件：stash 版与 HEAD 版比；一致 = 直接过
git diff "stash@{0}:<path>" "HEAD:<path>"

# 不一致的：把 stash **新增的每一行**拿去 HEAD 的同名文件里找，
# 找不到的再人工看是不是"换了措辞的同一件事"
git diff "stash@{0}^1" "stash@{0}" -- <path> | grep '^+' | grep -v '^+++'

# 未跟踪那一档（^3）：确认现在要么已被跟踪、要么确实不需要
git ls-tree -r --name-only "stash@{0}^3"
```

### ⚠️ 最要命的一条：**用来证明"可以安全删除"的那份核对，自己失败时报成了通过**

那次核对第一遍的输出是「扫到 0 行新增、缺 0 行」，6 个文件**看起来全过** ——
实际是临时目录不存在、`> added.txt` 的重定向**全部写失败**，
于是每个文件都在拿**空集**去比对，而空集当然"一条都不缺"。

**它证明的不是"内容都在 HEAD 里"，是"我什么都没检查"。**
而这份核对的用途是给一个**不可逆动作**（`git stash drop`）背书 ——
**一个失败时报成通过的检查，比没有检查更危险**：没有检查时人会犹豫，
有一份绿的检查时人会直接动手。

所以：**任何"逐条比对"的脚本，第一条断言必须是"我真的扫到东西了"**
（⑤A-2「空集返回绿」那一族的第 N 次；这一次咬的是核对工具自己）。
加上前提自检之后，真实数字才出来：30 / 27 / 23 / 25 / 34 / 113 行。

**那次的实际结论**（可作为范例）：12 个已跟踪文件里 3 个与 HEAD 逐字一致、
9 个是受害方重做后的**更新版本**（其中 `D-20` 那份 HEAD 版比 stash 版晚一天，
还订正了 stash 版里挂反的 ISC/MIT 署名 —— **pop 下去正好把订正盖掉**）；
未跟踪 2 个里 1 个已被提交跟踪且逐字一致，另 1 个只存在于 stash 里
（一个文件头写着「临时复现脚本，不提交，跑完删除」的 scratch 文件）——
**按第 3 条停下来报了 Manager，没有自行 drop**；
Manager 依据四件事裁定可以 drop，**这才拆掉**（2026-08-10）：
那个文件自己的第一行（作者本人写下的处置意见）、工作已重做提交、
结论已逐字进 HEAD、以及 `/tmp` 留有副本。

> **整条链条值得记住的形状**：不可逆动作 ← 需要证据 ← 证据来自一份核对
> ← **而那份核对本身可能是假绿**。链条上任何一环无声失败，最终结果都是"删得很有把握"。

### §15-ter `git checkout -- <file>` 是同一族，而且**更隐蔽**

`git stash` 那条讲的是「作用域比使用者以为的宽」。**同一个形状还有第二个入口，
而且它伪装得更好**：

```bash
# 变异验证的标准收尾动作 —— 本意是"撤销我刚注入的那几行"
git checkout -- apps/web/src/lib/format/jobName.ts
```

**它撤销的不是"刚注入的那几行"，是那个文件里全部未提交的改动。**

|                          | 使用者以为         | 实际                                 | 能不能找回           |
| ------------------------ | ------------------ | ------------------------------------ | -------------------- |
| `git stash -u`           | 收自己的改动       | 收走**整棵树所有人的**，含未跟踪文件 | 能（stash 对象还在） |
| `git checkout -- <file>` | 撤销刚注入的那几行 | 丢掉**该文件全部**未提交改动         | **不能，丢了就没了** |

⚠️ **为什么它更隐蔽**：它只影响一个文件，所以"作用域宽"这件事在直觉上不成立；
而它又恰恰是**变异验证的标准收尾**，而做变异验证的人**往往正好在那个文件上有未提交的工作**
—— 因为他关心它，才会去变异它。

`[真事，2026-08-10]` 另一路做变异验证时，排队命令的末尾就是上面那一行，
而同一个文件里还有他自己未提交的另一处改动（`CatalogLookups`）。
**那条命令没有执行，只因为 Bash 工具当时恰好不可用**，他改用备份文件还原了。
**纯属运气** —— 不是流程拦下来的。

规矩两条：

1. **撤销突变用备份文件，不用 git 命令。** 注入前 `cp <file> /tmp/<name>.bak`，
   验完 `cp /tmp/<name>.bak <file>`。**作用域恰好是你动过的那个文件的那一份内容**，
   与"这个文件里还有没有别的改动"完全无关。
2. **非要用 git 就先看一眼**：`git diff -- <file>`，确认里面**没有别的未提交改动**。
   ⚠️ **"我记得没有"不算。** 这与 §12 那句同源：
   **「我 add 完核对过了」在共享树里不成立 —— 核对的是过去，执行的是现在。**

**判据（与 §15 同一条）**：任何会**丢弃磁盘上未提交内容**的命令，
在共享树上都要先问一句「它的作用域是不是正好等于我以为的那个范围」。
`stash` 宽在"整棵树"，`checkout --` 宽在"整个文件"。

### §15-quater 证明"这是纯格式化"：前两个想得到的判据**都会误报**

格式化提交是**夹带修改的经典入口**（"就跑了个 prettier"这句话没人会去核），
所以它需要一个能站住的判据。`[实测 2026-08-10，四个文件]` 前两个想得到的都不行：

| 判据                                                          | 为什么不行                                                                                  |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `git diff --ignore-all-space`                                 | ✘ **prettier 会重排行**。换行位置变了不是"行内空白"，这条判据把**纯格式化**报成"有语义改动" |
| 去掉全部空白再比哈希                                          | ✘ prettier 断行时会**补尾逗号**（`1400,` / `true,`），去空白后仍有差异，同样误报            |
| ✔ **把 HEAD 版喂给 prettier，看是否与你提交的版本逐字节相同** | 它直接等价于**"我只做了 prettier 这一件事，零手工改动"**，而不是"我看着像没改语义"          |

```bash
a=$(git show HEAD:"$f" | npx prettier --stdin-filepath "$f" | sha256sum)
b=$(sha256sum < "$f")
[ "$a" = "$b" ] && echo '纯格式化' || echo '有手工改动，逐行看'
```

> **和 §15-ter 是同一类问题**：一个**看起来能证明的检查，其实证不了**。
> 区别只在后果 —— §15-ter 是"以为撤销的范围很小"，这里是"以为已经核对过了"。
> 两条都要先问：**这个判据在它该红的时候，真的会红吗。**

## 16. 一个"暂时不算数"的标记，会把一整族检查**静默**关掉

### 事故本体（T-196，用户真机撞上）

用户在 Windows v0.7.0 上报「whisper.cpp Vulkan 后端没得下载安装使用」。
根因是 `vendor/manifests/backends.json` 里那个包带着 `availability: "pending-ci"`
（"已构建、但还没有可下载的地址"），而前端据此把按钮 `disabled` 掉。
**包其实早就在 v0.6.0 的架上了** —— 标记写下时是实话，发布完没人回来翻它。

真正值得记的不是那两个字，是**翻对标记之后立刻多出来的两条红**：

```
✘ 每个可下载的包都必须在 components.json 里查得到来源与许可证
    → whispercpp-metal-macos-arm64, whispercpp-vulkan-win-x64
✘ macOS 包必须声明最低系统版本（它是量出来的，不是可选的装饰）
    → whispercpp-metal-macos-arm64 的 requiresDriver 是 null
```

这两条缺口**比标记本身早得多**。它们一直没红，原因很简单：

- 「每个**可下载的**包都要有伴随条目」—— `pending-ci` 的包按定义不可下载，**够不着**
- 「**published** 的 macOS 包必须声明 `macosVersion`」—— 判据里写着 `availability === 'published'`，**够不着**

> **一个 opt-out 标记，让三条检查同时休眠：按钮、伴随条目、系统版本声明。
> 而没有任何一处说过"这些检查现在不生效"。**

### 危险在哪：休眠是静默的

**检查没红，不是因为它通过了，是因为它压根没看。** 这两种状态在门禁输出里
长得一模一样 —— 与本仓「假绿灯家族」是同一个形状，只是这次关掉检查的
不是一段坏代码，而是**一条我们自己写下的、当时正确的元数据**。

而且它有**时间差**：标记写下的那一刻，被关掉的检查确实不该跑；
等条件变了（包发布了），标记不会自己翻，检查也不会自己醒。
**休眠期越长，攒下的缺口越多，而且没有任何计数器在涨。**

### 判据

> **任何 opt-out 标记，都要能被问一句：「它现在关掉了哪些检查？」
> —— 而且那份清单要写下来，写在标记的定义旁边。**

这条清单有两个用处，缺一不可：

1. **翻标记的人**知道自己一并唤醒了什么，会预期到那几条红（而不是以为自己弄坏了什么）；
2. **加标记的人**知道自己一并关掉了什么，从而判断这个代价可不可接受。

`[实测]` T-196 里正是第 ① 条救了场：翻完标记后 daemon 全量测试红两条，
如果没有"翻标记会唤醒检查"这个预期，最省事的读法是"我把清单改坏了"→ 改回去 →
缺口继续睡。

### ⚠️ 不许过度推广：要治的不是标记，是"关掉了什么没人知道"

**`pending-ci` 本身是对的设计**，它的原始理由就写在字段定义旁边
（`packages/shared/src/backends.ts:184-193`，`BackendPack.availability` 的文档注释）：

> Publishing a URL that 404s is worse than admitting the gap: the failure surfaces at
> click time instead of at review time.

「包构建出来了、URL 已知、但还没上架」是一个**真实存在且必须能表达**的状态。
禁掉它只会逼人二选一：上架前不许写地址，或上架后必须记得补地址 —— **两个都靠人记得**。

所以这一条**不是**"不许有 opt-out 标记"，是：

- 标记要有**能被问出来**的关闭清单（写在定义旁边）；
- 更好的做法是让**标记本身可被证伪** —— T-196 的做法是加一条
  `check-release-refs.mjs --assert-availability`：**`pending-ci` 的地址如果真的下得到 → 红**。
  它不禁止这个标记，只是不让它**说谎超过一次门禁**。
  ⚠️ 注意它**刻意不写成**"`pending-ci` 不许带 URL" —— 那会挡住上面那个合法用法。
  **判据钉的是后果（"你说下不到，那我下一下"），不是形式。**

### 同族（`availability` / `skipped` / `experimental` / `deprecated` / feature flag …）

任何"这条暂时不算数"的表达都属于这一族。接手时问三句：

1. 有多少条检查的判据里出现了这个字段？（`grep` 那个字段名，不是凭印象）
2. 这些检查在标记生效时**够不着**哪些对象？
3. 标记从"生效"翻回"不生效"时，**谁会告诉你那些检查醒了**？

第 3 句没有答案，就说明这个标记今天正在静默地关着东西。
