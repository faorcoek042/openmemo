## 三、回报重点：变异证明结果

判据是"这条腿必须能在按钮死了的时候真的红"。做法：给目标按钮挂一个**捕获阶段**监听器，
`stopImmediatePropagation()` + `preventDefault()` —— 按钮**还在、还可见、还可点、样式不变**，
但点击到不了任何处理器。**产品源码一个字节没改**（§10）。

```
正常：  「立即测速」 URL 没变 / DOM 变了 / 1 个 /api 请求  → 有反应 = true   ✔ B1 通过
变异后：「立即测速」 URL 没变 / DOM 没变 / 0 个请求 / 0 异常 → 有反应 = false → **B1 如期变红**
```

**这条腿看得见"按钮死了"。** 反过来说：如果它没红，我这条腿就是在用一个看不见问题的
判据去证明没问题 —— 那比没有这条腿更糟。

## 五、这条腿的取舍（写下来，免得被当成偷懒）

**只跑 ubuntu，不铺三平台。** 它抓的是「按钮有没有反应」，那是**前端代码**的性质 ——
同一份 JS 在三个平台跑同一套逻辑。用户在 Windows 撞见，但成因与操作系统无关，
`[实测]` 在 Linux 上一模一样地复现了。铺三平台会让一条几分钟的腿变十几分钟，换不到新事实；
而真正与平台有关的那些，本来就在无头浏览器能力之外。

**刻意不追求覆盖所有页面**（Manager 交代）。贪多会让它慢到没人跑，
一条没人跑的腿等于没有。先钉住"点击 → 有反应"。

**已知未修的死按钮用清单钉住，不是删掉也不是一直红**：
出现清单之外的死按钮 → 红；清单里的被修好了 → 也红（提醒划掉）。
理由是本仓吃过的那个亏：**一个永远红的门禁等于没有门禁**。
