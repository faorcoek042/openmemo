## ① 三态契约 —— **够格（3 次，且三种写法互不相同）**

| # | 位置 | 它怎么表达"第三态" |
| --- | --- | --- |
| 1 | `packages/shared/src/fitness.ts:74,291` | `features: string[]` **空数组** = 未知；另加正交字段 `cpuFeaturesUnverified: string[]` |
| 2 | `packages/shared/src/hardware.ts:104` | **两个 boolean 拼出三态**：`installed` / `probed` / `available`，靠一句注释维持不变式（原文：`available: true` always implies `probed: true`） |
| 3 | `apps/web/.../HardwareCard.tsx:56` | **组件里现算**：`hw.backends.some((b) => b.installed) ? 已查过没有 : 还没装所以没查` |

**三处是同一个形状：「不适用 / 未知 / 不支持」——而三处的写法完全不同**，
每一处都是撞上了才各自修的（AVX2 那次是用户报的，GPU 那格是我上一轮顺手发现的）。
**这正是阈值要的那种"各修各的"。**

**抽出来能挡住什么**：`cpuFeaturesUnverified` 那个字段是为了什么而加的，写在它自己的注释里 ——
**「共用一个槽位正是这个 bug 的成因」**。今天第 2 处仍然靠**注释**维持不变式
（两个 boolean 有 4 种组合，其中 `available && !probed` 是**非法**的，但类型系统允许它），
第 3 处根本没有类型，是组件里临时算的。

**建议的形状**（**未实现，供 Manager 裁决**）：一个让"第三态被塞进第二态"**编译不过**的联合类型，例如

```ts
type Tri<T> =
  | { kind: 'n/a' }                      // 不适用：这个维度在此平台不存在
  | { kind: 'unknown'; why: string }     // 未知：**必须说清为什么没测到**
  | { kind: 'known'; value: T };         // 已测：有证据
```

关键不是"三个分支"，是 **`unknown` 强制带 `why`**，以及**没有任何一个分支能同时表达
"没测到"和"测了没有"** —— 后者正是 AVX2 那个 bug 的形状。

⚠️ **代价要说清**：`BackendStatus` 是**跨进程契约**（daemon → 网页，还进了 `schemas.ts` 的
zod 校验）。换成联合类型要同时改 schema、daemon、web 三侧，而**其中 `apps/web` 现在有人在动**
（引导链第四种死法）。**所以我判断：形状够格，但此刻不是动手的时机。**

## ② 「消息必须说下一步」 —— **形状真的反复，但不该抽成强制**

Manager 数的 5 处属实（下载失败、VAD 装错、自检 blocked、测速未实现、数据目录残留）。
公共类型**已经存在**：`packages/shared/src/events.ts:187` 的 `interface Remediation`。
也就是说 **"共用一份定义"这一步早就做完了**，缺的是"强制"。

**但强制不成立，数字在这里**：

```
apps/daemon/src 里 sendError( 调用点 = 171
其中提到 remediation 的     ≈ 2
```

把 `remediation` 变成必填 → **一次性变红 169 处**。而那 169 处里绝大多数是
`INTERNAL` / `BAD_REQUEST` 这类**用户无法采取行动**的错误 —— 逼它们填，只会造出
169 条**假的 remediation**，而"给一个没用的下一步"比"不给"更糟：
用户照着做、没效果、然后不再相信任何一条提示。

**判断：不抽。** 真正的判据是「**这个错用户能不能做点什么**」，而**那不是机器能判的**。
⚠️ 也不许做成措辞正则 —— 一条靠散文措辞撑着的守卫，是一条会静默停止工作的守卫。

**可做的窄版（待观察，未实现）**：只对**已知可行动**的错误码（`MISSING_ASR_MODEL`、
`DISK_FULL`、`PROVIDER_UNREACHABLE`…）在类型上要求 remediation。
但那需要先把"哪些码是可行动的"列出来 —— **那份清单本身就是判断，不是提炼**。

## ③ 「对照组先行」 —— **出现 8+ 次，但没有东西可抽**

`shared/breaker.test.ts`、`daemon/http/guard.test.ts`、`daemon/http/rest/installWarmup.test.ts`、
`daemon/http/healthHost.test.ts`、`daemon/bootstrap/entrypoint.test.ts`、
`daemon/runtime/breakerRecovery.test.ts`、`web/features/notes/noteAssets.test.ts` …

**次数远超阈值。但逐个读下来，它们只是同一条纪律的三种完全不同的形状：**

- `guard.test.ts:238` —— 正向对照：「完全合法的请求必须通过」，证明下面三条不是"什么都拒"
- `breakerRecovery.test.ts:231` —— 负负对照：「恢复探测**也失败**时不许报好」
- `noteAssets.test.ts:151` —— 区分度对照：「只加一条 `audio16k` 就必须换人」

**三者没有共同代码。** 能被抽出来的只有一个空壳（"再写一个能区分的用例"），
而那不减少任何出错概率 —— **它是纪律，不是重复**。做成 helper 只会多一层仪式感。

⚠️ 也做不成守卫：**"哪一条是对照组"机器判定不了**（不能靠名字里有没有"对照组"三个字 ——
那又回到散文正则）。

**判断：不抽、也不守。** 它已经在 PROTOCOL 里作为纪律存在，那是它正确的位置。
