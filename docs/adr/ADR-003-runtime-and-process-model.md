## 决策 1：进程模型 = **本地 daemon + 浏览器 UI（web-first）**

用户要求原文："**使用网页接入**"、"通过**你设计的网页**完成"。据此定架构基线：

```
┌─ 浏览器（任意）─────────────┐
│  React SPA                  │  ← 唯一 UI，所有功能（含装 GPU 后端、管模型）都在这
└──────────┬──────────────────┘
       HTTP / SSE / WS  (127.0.0.1 ONLY)
┌──────────┴──────────────────┐
│  本地 daemon (Node.js + TS) │  ← 任务队列、硬件探测、下载器、DB
└──────────┬──────────────────┘
       子进程 spawn（崩溃隔离）
┌──────────┴──────────────────────────────────────┐
│ ffmpeg │ yt-dlp │ whisper-cli │ llama-server │ probe │
└─────────────────────────────────────────────────┘
```

**理由**

- 直接满足"网页接入"，无需先解决 Electron/Tauri 之争即可开工。
- 原生组件一律**子进程**调用 → 崩溃隔离（R-02 建议）、许可证隔离、可独立升级。
- 桌面外壳（Tauri v2 包一层指向 daemon）**后置为可选**，不进 v1 关键路径。

**安全硬要求**（来自 R-01 §B "不要照抄" 清单）

- 所有监听 **必须绑 `127.0.0.1`**，绝不 `0.0.0.0`（memo.ac 的 `whisper-server` 犯了这个错）。
- 插件沙箱**禁用 `vm2`**（已废弃 + 已知逃逸漏洞），需要沙箱时用 `node:worker_threads` + 权限白名单。
- daemon 启动生成随机 token，网页需带 token 才能调 API，防止其他本地进程/恶意网页打我们的端口。

## 决策 3：GPU 后端策略

基于 R-02 的实测（ggml `GGML_BACKEND_DL=ON` → 后端是可热插拔的独立 `.dll/.so`，
CPU 包与 CUDA 包结构 100% 一致，差集仅几个文件）：

**要求 2.1 的实现 = 往同一目录多丢几个文件。** 这是一等公民能力，不是 hack。

**降级链（L0 → L2）**

| 档  | 内容                             | 体积        | 何时用                         |
| --- | -------------------------------- | ----------- | ------------------------------ |
| L0  | 浏览器 WebGPU（transformers.js） | 0（零安装） | 首次打开即可试用，不装任何东西 |
| L1  | 内置 CPU 后端                    | 8–20 MB     | 永不失败的兜底                 |
| L2  | 按需下载加速后端                 | 见下        | 网页点一下装                   |

**NVIDIA 默认后端**：采纳 `gpu-runtime` 的临时立场 —— **Vulkan 为默认**（~30 MB），
**CUDA 作为可选高性能包**（实测 677.9 MB）。理由：678 MB vs 30 MB 差 22 倍，
而**性能差距 = UNKNOWN**（R-02 诚实地拒绝编造：whisper.cpp 官方 bench 帖只有 CPU/WASM 数据）。
→ **spike 实测后可推翻本决策**，这是临时立场不是终局。

**探测硬要求**：文件存在性检测**不可信**（R-02 在本机发现反例：`libvulkan.so.1` 存在但无 GPU、
无 `/dev/dri`）→ 必须真正枚举设备。probe 跑独立子进程 + 10s 超时 + ~~失败熔断~~
**失败熔断 + 冷却期/半开**。
⛔ **原文只说了"怎么进去"，没说"怎么出来"** —— 照着它实现出来的东西不是断路器，是死锁：
拉黑之后唯一的解除条件是探测成功，而成功的前提是被调用、被调用的前提是没被拉黑。
**订正与实测见文末 §8（2026-08-08）。10s 与阈值 2 一个字未改，改的只有"出来"那一半。**

**自检**：安装后跑内嵌测试音频做**真实推理**（memo.ac 的做法，值得照抄），测出 RTF 展示给用户。

## 决策 5：离线全量安装包 —— **不进 v1**

~~`gpu-runtime` 决策项 4 否决。个人自用场景无内网刚需，750 MB+ 的打包成本不值得。~~

**这条仍然成立，但 2026-08-08 需要划清一个此前没有划清的边界**（Manager 裁决，
`e2e-coldstart` 就地订正，PROTOCOL §13：裁完之后回去改原文，而不是另加一段）：

> **「离线全量安装包」被否，不等于「引擎也不能随包出厂」。**

被否的仍然是**全量**那一种：把 **GPU 后端（`libggml-cuda` 单个就 564 MB）+ 模型
（推荐的 ASR 就 574 MB）** 全塞进包里，750 MB+ 起步。那条判断没有变。

**同日新增、且不受本条约束的是「CPU 基线运行时」**：

|              | 离线全量包（**仍然否**）    | CPU 基线运行时（**2026-08-08 采纳**）                                                                                                                    |
| ------------ | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GPU 后端     | 含（`libggml-cuda` 564 MB） | **不含**                                                                                                                                                 |
| 模型         | 含（574 MB 起）             | **不含**                                                                                                                                                 |
| CPU 转写引擎 | 含                          | **含**（whisper-cli + libwhisper）                                                                                                                       |
| 增量体积     | 750 MB+                     | **linux 1.82 MB / macOS 1.66 MB / win 2.11 MB**（`[本机实测 2026-08-08]`，与探针共用 ggml 之后的**增量**；三件 = whisper-cli + libwhisper + VAD 切分器） |

采纳的依据（三条，都不是"体积可以接受"这种程度的理由）：

1. **许可证理由不成立。** whisper.cpp 是 **MIT** —— D-17 §1 那条 GPL 顾虑只对
   ffmpeg / yt-dlp 成立，对 whisper.cpp 从来不成立。所以"不打包引擎"此前**只剩体积理由**。
2. **它补上一个从未被验证过的洞。** 本 ADR **决策 3** 的 L1「永不失败的兜底」
   `[实测]` **一次都没有被验证过** —— 因为兜底要用的那个包根本不在包里
   （同一轮里 §10 已就地订正探针那一半）。一个没有实现的兜底不是兜底。
3. **对照 memo.ac 量出的结构差距**：它把引擎装在盒子里，我们发的是一个安装器。
   从新用户到第一次转写，可失败环节我们比它多。

⚠️ **不要把这条读成"以后什么都可以往包里塞"。** 判据是那张表的四行：
**不含 GPU 后端、不含模型、只含 CPU 基线、增量在个位数 MB**。
四条里任何一条不成立，回到本条的原始否决。

# 附录 A：T-012 实测结果与由此产生的硬约束（2026-08-02）

`gpu-runtime` 在本机（Linux x86_64，**无 GPU**）真编译、真跑数。以下**全部是实测，非推断**。

## A.1 要求 2.1 已实证闭环 ✅

- **`GGML_BACKEND_DL` 论断证实**：`ldd libwhisper.so` 只有 `libggml.so.0` + `libggml-base.so.0`，
  12 个 CPU 后端**一个都不链接**，运行时自动选中 `zen4` 变体。
- **丢进 1 个 `.so` → Vulkan 后端加载成功，无需重装、无需重启。包完全可重定位。**
- **L2 加速包 = 恰好 1 个文件，22.7 MB**（tar.gz）；L1 core 仅 **7.70 MB**。R-02 的体积外推成立。
- 装了用不上的 Vulkan 包 **零损耗静默回落** → 降低"默认推 Vulkan"的决策风险。

## A.2 第一批真实性能数字（11.0s 音频 / 8 线程 / 各 3 次）

| 变体              | RTF         | 倍速 |
| ----------------- | ----------- | ---- |
| `tiny.en`         | 0.027–0.029 | ~35x |
| `base.en`         | 0.040       | ~25x |
| 强制 `sse42` 兜底 | 0.094–0.103 | ~10x |

→ **最优与最差 CPU 变体差 3.4 倍。** 这不是可忽略的差异。
**硬约束**：CPU 微架构变体的选择必须做对（不能一律发 `sse42` 保险牌），
否则用户白白损失 3.4 倍性能。写入 `packages/runtime` 的选择逻辑。

## A.3 三条新增硬约束（均由实测反例催生）

1. **probe 必须跑子进程 —— 从"建议"升级为"刚需"。**
   实测：删光 CPU 后端后 ggml 走 `ggml_abort()` → **SIGABRT(134)，不是返回错误**。
   进程内捕获不了，同进程 probe 会直接杀死 daemon。
2. **L1 内置 CPU 包是承重墙，任何情况下不可移除。** 同上，没有它就是 SIGABRT。
   模型/后端管理 UI **必须禁止用户删除 L1 CPU 包**。
3. **GPU 探测：`枚举数 > 0` 同样不可信。**
   实测：lavapipe（软件光栅化）让**无 GPU 的机器报告 1 个 Vulkan 设备**（`deviceType=CPU`）。
   → 继 R-02 的"文件存在性不可信"之后的第二个反例。**必须检查 `deviceType`，
   排除 `CPU`/软件实现**，否则会把 CPU 当 GPU 用，性能反而更差。

## A.4 未完成（如实记录，非"应该能"）

- **CUDA / ROCm 未编译** —— 本机无 SDK 无硬件。是**没编**，不是"应该能编"。
- **CUDA vs Vulkan 性能比仍是 UNKNOWN** —— 决策 3（Vulkan 为默认）**仍是临时立场**，
  需要一台有 NVIDIA 卡的机器做 spike 才能定案。已上报用户。
- `.github/workflows/build-backends.yml` **从未执行**（无 git remote）。

## A.5 过程记录

`gpu-runtime` 自测时抓到自己一个真 bug：`backendUsed` 误报 Vulkan
（混淆了 "loaded" 与 "used"），已修并复测。**自检能抓出自己的 bug，说明自检设计是有效的。**

## 7.2 今天用户到底会不会被 Gatekeeper 拦 —— `[未验证：需真 Mac]`

**取不到。本轮执行环境是 Linux，没有任何 macOS 机器，CI 的 macOS runner 也是非交互的**
（`D-11` 已记：runner 上没有 Finder、没有 LaunchServices 会话，
`ADR-012:61-68` 那条"最大验证缺口"至今成立）。

**不要靠推断下结论。** 下面把两条**必须分开**的路径写清楚，各自标级别：

| #   | 路径                                                                                                | quarantine 会不会被打上                                                            | 级别                                                 |
| --- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------- |
| ①   | 用户在**浏览器里**下载 OpenMemo 的发布包，再用 Finder 解压                                          | 浏览器属于 LaunchServices 的 quarantine-aware 应用，解压时属性会传播给解出来的文件 | `[报告]`（Apple 的公开行为，**本轮没在真机上验过**） |
| ②   | **daemon 自己**下载后端包（`packages/downloader`，走 undici/Node，再由我们自己的 `unpack.ts` 解压） | 这是普通的文件写入，不经过 LaunchServices                                          | `[未验证]` — 这是**假说**，正是最该验的一条          |

**为什么这个区分是决定性的**：ADR 原文写的是"**首次运行时由 daemon 自动清除**" ——
它针对的是路径 ②。**如果 ② 根本不会被打上 quarantine，那这条缓解措施从一开始就没有必要，
"缺了一环"的其实是论证，不是代码。** 反过来如果 ② 会被打上，那今天每一个加速包在 Mac 上
都可能加载失败，而我们没有任何补救。**这两种结论差别极大，而它们只差一条命令。**

### 验它需要什么（一条命令，任何一台 Apple Silicon Mac，5 分钟）

```bash
# 路径 ②：让 daemon 真装一个后端包，然后直接问文件
xattr -p com.apple.quarantine <models_root>/runtime/<pack>/libggml-metal.so ; echo "exit=$?"
#   exit=1 且报 "No such xattr"  -> ② 不会被打上 -> 缓解措施本来就不需要 -> 改 ADR 收工
#   打印出 0083;....;Safari;    -> ② 会被打上   -> 今天 Mac 用户是坏的 -> 见 §7.5

# 对照组，证明这台机器确实会打 quarantine（否则上面的阴性结果没有意义）
curl -LO <任意 http 链接>   # curl 不会打
# 换成用 Safari 下同一个文件，再 xattr -p —— 两者不同才说明探针有效
```

⚠️ **阴性对照是必需的**：`xattr -p` 在"这台机器压根不打 quarantine"和
"这个文件没被打"两种情况下输出一样。没有对照组的阴性结果等于没测 —— 本仓栽过三次。

## 7.4 为什么必须就地改，而不是在别处挂警告

`build-backends.yml:207` 的作者做对了 90%：他发现了、他写下来了。
**但他写在了一个读 ADR 的人永远不会经过的地方。**

于是这条缺陷获得了最坏的一种状态：**"有人知道"和"没人知道"在后果上完全相同，
而台账上它看起来像被处理过了。** 之后又有至少两轮审计重新发现了同一条
（`platform` T-141 §3.0-③、`closure-audit` 🟡-4）—— 每一轮都付了一次全仓 grep 的钱。

> **判据：一条不实的断言，只能在它被读到的那一行修。
> 在别处挂警告，是把发现的成本留给了下一个人。**

这与 PROTOCOL §7 的成因是同一个形状（"两句话隔了 60 行，读到禁令的人不会意识到自己
刚敲的命令违反了它"）。所以本轮**改了决策 4 那两行本身**。

## 7.5 需要拍板：补实现这件事**不能由 agent 自己做**

看起来"补一个 `xattr -dr` 就行了"。**本轮刻意没有补**，理由是判断，不是偷懒：

1. **清除 quarantine 就是关掉 Gatekeeper 对我们自己产物的检查。**
   它属于 Security Weaken 一类的改动，与"绑 `0.0.0.0`"、"放宽 Host 校验"同级，
   本项目的既定做法是**必须用户本人在自己的轮次里说**（见 `closure-audit` 🚧-14）。
2. **在 §7.2 那条命令跑出结果之前，我们不知道它解决的是不是一个真实存在的问题。**
   给一个未经确认存在的问题写一段无法在本机验证的缓解代码，正是本仓最贵的那类改动。
3. 真要补，`xattr` 也不该是唯一选项：ad-hoc 签名 + 用户首次手动放行（右键打开）

## 8.1 缺陷：那不是断路器，是死锁

决策 3 只写了"失败熔断"，没写熔断之后怎么解除。照它实现出来的代码是
（`packages/runtime/src/probe/runProbe.ts`，T-173 之前）：

```ts
blacklistedAt: consecutiveFailures >= CIRCUIT_BREAKER_THRESHOLD
  ? (state.blacklistedAt ?? new Date().toISOString())   // 置上之后再也不会被失败清掉
  : null,
```

`recordProbeOutcome()` **只在成功时**清 `blacklistedAt`。于是：

> 解除拉黑的唯一条件是**探测成功**；
> 探测成功的前提是**探针被调用**；
> 探针被调用的前提是**没被拉黑**。

**这个环没有出口。** 用户收不到任何报错，只会发现 GPU 加速"就是不工作"，然后无从下手。

指纹变化不是出口：它只兑现**一次**重试（`recordProbeOutcome` 随即把新指纹写回 state，
裁决带着新指纹重新关上），而**包装好之后指纹从此不再变**。

### 它在真实机器上必然发生（T-172 实测，不是推演）

macOS 冷机器上 Metal shader 缓存首次初始化 **12–21 s**
（`[实测]` n=4：12306 / 16092 / 17606 / 20959 ms，CI run 31198373722 等），
**四个样本全部 > `PROBE_TIMEOUT_MS`（10 s）**。而一个 daemon 进程里正好有两个独立调用点
（`RestState.create()` 与首个 `GET /api/runtime/hardware`）⇒ **两次超时 ⇒ 必然跳闸**。

T-172 已经用"装包时捂热"修掉了**装包那条路**（捂热正好落在指纹放行的那一次重试之前，
把它从必然失败变成必然成功）。**但残留一条**：包已装好、**之后**缓存才变冷
（系统升级清了 shader 缓存 / 换用户账户 / 缓存被回收）。那时没有装包动作 → 不捂热 →
指纹不变 → 同样永久拉黑，**且零报错**。

## 8.2 裁决与修法：给它冷却期（半开）

Manager 裁决原文：**"拉黑之后唯一的解除条件是成功，而成功的前提是被调用，
被调用的前提是没被拉黑。这个环没有出口。"** 修法方向是断路器的标准形状 ——
超过冷却时间放行一次探测，成功即彻底复位，失败就重新计时。

落地为三态裁决 `breakerVerdict()`：`closed` / `open`（冷却中，一发不探）/
`recover`（半开，放一发）。**不变式：`blacklistedAt !== null` ⇒ `retryAt !== null` 且必然到期。**

| 参数                        | 取值                                             | 依据                                                                                                                                                                                                                                                                                           |
| --------------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BREAKER_COOLDOWN_MS`       | **60 s**                                         | **下界**由"不许做成每次自检都重试"夹出来：诊断页自检查询 `staleTime` 是 30 s，用户手动刷新更密；60 s ⇒ 无论怎么刷，一分钟内最多放一发。**上界**由"残留情形要在用户察觉前自愈"夹出来。                                                                                                          |
| `BREAKER_COOLDOWN_MAX_MS`   | **1 h**（指数退避 60s→2m→4m→8m→16m→32m→1h 封顶） | 每发恢复探测的代价是**一个后台子进程**，不是用户的等待（见下）。封在 1 h ⇒ 驱动真挂死的机器每天最多白跑 ~24 发；而用户**修好驱动后一小时内产品自己发现**，不需要他知道有个断路器存在。                                                                                                         |
| `PROBE_RECOVERY_TIMEOUT_MS` | **90 s**                                         | ★ **不能沿用 10 s**：冷 Mac 上恢复探测要 12–21 s，而被 kill 的探针**什么都不留**（shader 缓存全有全无，T-172 已证伪"部分落盘"）⇒ 10 s 预算下每次必然超时，只是从"永久拉黑"变成"永久重试"。90 s ≈ 最大观测样本 ×4（真机 M 系列的数 **UNKNOWN**，取不到），与 `warmup.ts` 的捂热预算同源同理由。 |

**半开那一发跑在后台，不在交互路径上。** 就地探等于让用户的请求最长挂 90 s ——
比原来的病还重。当次请求立刻返回"仍停用 + 正在重试"，恢复跑完自己改 state。
并发控制是**单飞**（每个 `backendDir` 至多一发）：不去重的话，冷却到期那一刻的十几个
并发请求会同时 spawn 十几个探针去抢同一块 GPU 初始化 —— 那正是断路器本该防住的
"猛敲一个坏掉的东西"。

**顺带**：`GET /api/runtime/breaker` 以前会 `await detect(false)`，缓存空时**查一眼断路器
就真跑一发探测**（冷机器上 10 s，失败还会把计数加一）。一个看一眼就改变被观测对象的
排障入口，测出来的是它自己造成的状态。现在走纯观测。

## 8.3 **两个常量一个字未改**

`PROBE_TIMEOUT_MS = 10_000`（多久算超时）与 `CIRCUIT_BREAKER_THRESHOLD = 2`（几次算坏）
**均未改动**，测试直接断言其值。这次改的是"停用之后怎么出来"，不是"多久算超时""几次算坏"。
抬高 10 s 的代价由**每一次真故障**来付（决策 3 引 ROCm 驱动挂死），T-172 已论证过。

## 8.4 静默降级必须被看见（这一条比冷却期本身更重要）

跳闸此前是**零报错**的：`runtime.breaker` 确实随 `/api/runtime/hardware` 发出去，
但前端把响应断言成窄契约 `GetHardwareResponse`，那个字段**在类型边界上就被丢掉了**，
全仓前端对 `breaker` / `blacklistedBackends` / `degradationChain` 的引用数是 **0**。

> **一个能自愈、但用户不知道发生过什么的系统，和一个坏了不吭声的系统，在用户那里是一样的。**

所以自检新增检查项 **`hw.breaker`**（layer `hardware`，`status: warn`、`required: false`
—— CPU 兜底还在，产品能用，不该让 CLI EXIT=1），中英各一份，daemon 与 CLI 两个出口都接上。
`CheckResult` 相应增加**可选**的 `detailEn` / `remediationEn`（历史那 24 条的 `detail`
一直是中文原文，前端回退方向是"没有英文版就显示中文原文，**绝不回退到空**"——
回退成空会让一条真实告警在英文界面上消失）。

## 10. 订正决策 3（2026-08-08，`prebuilt` 就地改，Manager 当轮授权）：L1 此前**从来没有被验证过**

> 六个后端（含 `cpu`）全部得到 `probe did not complete: probe executable not found` ⇒
> **连 L1 这一档也只是推断，不是实测。**

`[用户真机实测 2026-08-08, Windows, v0.3.0]` 用户解压即运行，本机组件页
六个后端全部是那一行。`[本机复现, linux-x64, 全新空数据目录]` 一模一样。

**订正**：预编译包现在自带最小探针运行时（`runtime/probe/`：探针 + ggml 核心

- 一个 CPU 后端模块，`[实测]` 1.60 MiB）。于是：

| 档             | 此前                                                    | 现在                                                            |
| -------------- | ------------------------------------------------------- | --------------------------------------------------------------- |
| L1（CPU 兜底） | ~~声称"永不失败"，**但没有探针，从未被枚举验证过**~~    | **实测**：`cpu available=true probed=true`，探针枚举出 1 个设备 |
| L2（加速后端） | 六个后端一律报 `probe did not complete`（吓人且没信息） | 未装的报 **`backend package not installed`**（真话）            |

⚠️ **L2 的"能不能用"在装之前仍然不可验证，这是结构性的，不是待办**：
探针只能枚举与自己同目录的后端模块，而 `libggml-cuda.so` 本身 564 MB ——
那正是用户要决定装不装的东西。**本 ADR 不应被读成"探测能告诉你该装哪个加速包"** ——
它能告诉你的是**硬件与驱动**（advisory 层：`nvidia-smi` / `lspci` /
`system_profiler` / `wmic`），以及**装完之后那个包是不是真的能用**（探针层）。
两个问题，两层证据，不要混为一谈。

详细依据、体积代价、查找顺序约束与反向验证见 `ADR-015 §7.5` 与 `docs/design/D-17`。
