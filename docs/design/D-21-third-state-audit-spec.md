## TL;DR（≤ 25 行，Manager 只读这里）

- 这是给 **#90 审计者**的**判据文档**，不是回执，也**不含任何"我实现得对不对"的自评** —— 那是审计者的活。
- **为什么要有它**：#87 那一批修复的守卫**只证明了字符串出现在 jsdom 容器里**，
  **没有一条证明人看得懂、能照着做**。`t.includes('EACCES')` 通过，不等于用户知道该干什么。
  那是这条线**最后一层没被覆盖的东西**。
- **分工**：作者（我）陈述**意图**，审计者检查**现实是否匹配**。
  没有判据的审计只能靠审计者猜设计意图 —— 那等于换个人再犯一次"拿写作时的意图当判据"。
- 🔴 **第 3 列「可操作性」必须单独判，不许并进文案里读。**
  本批有两处改的**就是可操作性**：GC 按钮在"未知"时**改为可点**、
  UNKNOWN 那一档**刻意不给动作按钮**。**一个只查字的审计会把这两处都记成"通过"** ——
  也就是把本批唯一真正改变了"用户能做什么"的地方，全部漏掉。
- 🔴 **「有按钮」和「按钮点了有用」是两件事。** 本轮删过「点得动、跳得走、就是到不了能修的那一页」的按钮。
  所以每个动作都写明**终点应该是哪儿**；到不了那个终点 = 这一格失败。
- **工具**：仓里那条驱动 chromium 的 `e2e-browser` 腿才是该用的东西 —— 要**真的点**，
  并且要读**按钮的 disabled 属性**，不是只读文本。
- **未验证**：本文只写"应该是什么"。**每一格的真实表现一律未验**，由审计者填。

## 0. 怎么用这份文档

每个界面一条，四项：

| 列                 | 问的是                                               | 审计者怎么用                                         |
| ------------------ | ---------------------------------------------------- | ---------------------------------------------------- |
| **① 该说什么**     | 这一档**应当传达**的意思（不是现在写了什么）         | 屏幕上那句话传达到了吗？                             |
| **② 正确的下一步** | 用户看完**应该去做什么**；**或者明确"什么都不该做"** | 界面有没有把他导向这个动作？                         |
| **③ 可操作性**     | 该不该有按钮 / 启用还是禁用 / **按钮终点在哪**       | **单独判。** 读 `disabled`，并真的点一次看落在哪一页 |
| **④ 判失败的反例** | 一个**可判的**坏表现                                 | 看到它 = 这一格失败，不需要再讨论"看着对不对"        |

⚠️ **③ 与 ① 不许合并判。** 一句话说得再对，按钮该禁用却可点（或反过来），这一格仍然是失败的。

⚠️ **本文所有"第三态"共享一条总判据**：

> **「我不知道」不许被说成「没有」，也不许被说成「有」。**
> 三态各自有自己的话；把第三态渲染成前两态中的任何一个，都是失败。

## 1. 首屏横幅 · `toolchainUnknown`

**触发**：daemon 明确报 `pipeline.missing = null`（它没能确认工具链），而不是字段缺席。

|                    |                                                                                                                                                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **① 该说什么**     | 两件事，缺一不可：**(a) 我们没能确认工具链装齐了没有**；**(b) 因此新任务不会开始**。<br>⚠️ **只说 (a) 不够** —— 用户会以为只是一条提示，而实际后果是他的任务不动。                                                    |
| **② 正确的下一步** | **没有"去装什么"这个动作**（此刻我们连缺什么都不知道）。<br>他可以做的只有"再看一眼"，而那由诊断页那颗「重新检测」负责。                                                                                              |
| **③ 可操作性**     | **不该有动作按钮。**<br>理由：按钮只能把他送到 `/runtime` 或 `/models`，而**我们说不出他到了那儿该做什么** —— 那正是本轮删掉的「点得动、跳得走、到不了」。                                                            |
| **④ 判失败的反例** | · 横幅**一个字都不说**（最原始的那个 bug：任务不动，屏幕上什么都没有）<br>· 说成「缺少 N 个组件」（把"不知道"说成"知道缺什么"）<br>· **出现了动作按钮**（无论点了去哪）<br>· 只说"没能确认"、**不说"新任务不会开始"** |

## 2. 首屏横幅 · `pipelineUnavailable`（本平台没有可下载的包）

**触发**：缺的那些组件，**本平台目录里没有可下载的包**（目录事实，不是平台能力推断）。

|                    |                                                                                                                                                                                                                                   |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **① 该说什么**     | 主语是**我们/目录**：「**我们还没有为这台机器提供下载**」。<br>⚠️ **不许说成「你的平台不支持」** —— 那是一句关于用户机器的、我们没有依据的断言。<br>并且要说出后半句：**装到系统 PATH 上我们会直接用**，**但装好后要重启**。      |
| **② 正确的下一步** | 自己去系统里装（brew / apt / 官网），**然后重启产品**。<br>⚠️ **"要重启"这半句是动作的一部分，不是补充说明** —— 少了它，用户照做之后看不到变化，会认定产品坏了。                                                                  |
| **③ 可操作性**     | **不该有动作按钮，也不该报体积/耗时。**<br>理由：按钮会把他送到 `/runtime`，而那页会把这些包如实渲染成「其它平台」；报体积等于**承诺一次并不存在的下载**。                                                                        |
| **④ 判失败的反例** | · 出现体积（`MB`/`GB`）或耗时（「几分钟」）—— 包括**显示名里自带的体积**<br>· 出现「去修复 / 去安装」按钮<br>· 说成「你的平台不支持」<br>· **少了「装好要重启」那半句**<br>· 同一个显示名重复出现（ffmpeg 与 ffprobe 同名未去重） |

## 3. 诊断页 · 工具链那一格（`warn`）

**触发**：同 §1（`missing === null`）。

|                    |                                                                                                                                                                                                                                                      |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **① 该说什么**     | 「**没查出来**」，并给出**为什么没查出来**（原因原文）。<br>⚠️ 它**既不是「正常」也不是「故障」**：产品没坏（CPU 兜底还在），只是我们没能确认。                                                                                                      |
| **② 正确的下一步** | 点这一页的「**重新检测**」再试一次。除此之外**没有该做的事**。                                                                                                                                                                                       |
| **③ 可操作性**     | 这一格**不该有「去修复」**（连缺什么都不知道，送他去哪一页都是猜）。<br>「重新检测」按钮**该在页面上、该可点**；点击期间**该禁用并有进行中的迹象**（它真的会重新解析，代价随用户 PATH 长度走）。                                                     |
| **④ 判失败的反例** | · 这一格是**绿色/「正常」** ← **本批最严重的一处，排障页上说一切正常**<br>· 这一格是红色「故障」（把一次没测成说成功能坏了）<br>· 出现「去修复」按钮<br>· 只说"没查出来"、**不给原因**<br>· 「重新检测」点下去**看起来是瞬时的**（无任何进行中迹象） |

## 4. 数据目录搬迁 · 「读不到旧目录」

**触发**：删源失败**且**随后 `readdir` 也失败（两者高度相关：EPERM、目录被占）。

|                    |                                                                                                                                                                             |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **① 该说什么**     | 三件事：**(a) 我没能读到那个目录**、**(b) 原因**、**(c) 所以我不知道里面还剩什么**。<br>⚠️ **不是「空了」，也不是「没空」。**                                               |
| **② 正确的下一步** | **删那个旧目录之前，自己先去看一眼。**<br>⚠️ 这是本文里**风险最高**的一格：用户此刻正在判断"我的数据搬完没有"。<br>说成「已经空了」的代价是 **他去删一个还有东西的目录**。  |
| **③ 可操作性**     | 这是一段**文案**，不该有"一键删除旧目录"之类的动作。<br>如果界面提供了任何"帮你清理"的按钮 —— **在这一档下它必须不可用**（我们不知道里面有什么，不能替他删）。              |
| **④ 判失败的反例** | · 出现「**已经空了**」<br>· 出现「里面还剩下：…」却**没有列出任何东西**（等于用肯定句式说空话）<br>· **不给原因**（用户无从判断该怎么办）<br>· 提供了可点的"清理旧目录"动作 |

## 5. 存储页 · GC 按钮（未知时**改为可点**）

**触发**：`reclaimable.unclaimedBytes` 缺席（老 daemon / 没算出来）。

|                    |                                                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **① 该说什么**     | 「无法识别的残留」那一项应显示「**未知**」，**不是 `0 B`**。                                                                                                                   |
| **② 正确的下一步** | **可以点一次回收。** 不知道有多少可回收 **≠** 没有可回收的。                                                                                                                   |
| **③ 可操作性**     | 🔴 **这一格的重点全在这里。**<br>· 未知 ⇒ 按钮**必须可点**（enabled）<br>· 只有**每一项都数得出来且都是 0** 时，按钮才该禁用<br>· 终点：点击应触发回收本身，不是跳转到别的页面 |
| **④ 判失败的反例** | · 那一项显示 `0 B`<br>· 🔴 **未知时按钮是禁用的** ← **纯文本审计会漏掉这一条**<br>· 已知且全部为 0 时按钮却可点（反方向的失败，同样要判）                                      |

## 6. 后端卡片 · 三档芯片

三档必须**互相说得清**，任何两档长得一样就是失败。

| 档               | ① 该说什么                                                               | ② 下一步                             | ③ 可操作性                                                                   |
| ---------------- | ------------------------------------------------------------------------ | ------------------------------------ | ---------------------------------------------------------------------------- |
| **随产品自带**   | 这条算路**不需要装任何包**就能用（出厂自带那份在跑）                     | **什么都不用做**                     | 安装按钮**仍可点**（装一次是有意义的：改用产品自己那份），但**不该显得必须** |
| **本平台不适用** | 这个后端**在这个操作系统上根本不可能存在**（Metal/Core ML 之于非 Apple） | **什么都不用做，也没有任何东西可装** | **不该引导安装。** 不许报体积                                                |
| **未安装**       | 平台上**装得了**，只是还没装                                             | **去装它** —— 这一档才该引导安装     | 安装按钮可点，终点是真的开始安装                                             |

**④ 判失败的反例（本节共用）**：

- 「本平台不适用」被显示成「未安装」← **原始现场**：Windows 上 `metal`/`coreml` 说「backend package not installed」，
  等于**叫用户去装一个不存在的东西**
- 「随产品自带」被显示成「已安装」（那是"装了一个包"，这是"根本不需要包"）——
  并且会与同页下方「可安装 · N MB」自相矛盾
- 「本平台不适用」那一档**给出了安装按钮或体积**
- 同一张卡上，芯片说「可安装」而按钮说「暂不可安装」（**同屏两句打脸的话**）
- **⚠️ 反方向**：一台 Mac 上的 CoreML 被标成「其它平台」（那是假的 ——
  它没有可下载的包，但平台上是可能的。**没有包 ≠ 平台上不可能**）

## 7. 模型卡 · 「使用中但读不了」三分支

**触发**：`active` 指着一份**本机引擎加载不了**的权重。

| 分支                 | ① 该说什么                                             | ② 下一步                     | ③ 可操作性                                                                              |
| -------------------- | ------------------------------------------------------ | ---------------------------- | --------------------------------------------------------------------------------------- |
| **已装一份读得动的** | 「使用中」不等于真的用上了；**你已经有一份它读得动的** | **改用那一份**               | 该给动作，终点是**真的把 active 切过去**                                                |
| **确知没有读得动的** | 本机也没有一份该引擎读得动的                           | **去装一个标着该引擎的变体** | 该给动作，终点是安装那个变体                                                            |
| **说不出（第三态）** | 「另一份能不能用，**这次没查出来**」                   | **什么都不该做**             | 🔴 **一个动作都不给。**<br>理由：我们不知道该建议切换还是建议安装，**给任何一个都是猜** |

**④ 判失败的反例**：

- 第三态给出了「改用那一份」或「去装一个」——**在不知道的情况下替用户选了一边**
- 第三态被静默处理（卡片什么都不说，而 active 指着一份跑不了的权重）
- 「已装一份读得动的」那一档的动作点下去，**active 没有真的改变**

## 8. 代理设置 · 「无法判定」

**触发**：有探针失败，但**分不清是代理的问题还是目标站的问题**。

|                    |                                                                                                                                                                  |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **① 该说什么**     | **两侧都不许被排除**：这次失败**不能**归给代理，也**不能**归给目标站。                                                                                           |
| **② 正确的下一步** | **展开看每一条的原始错误再判断。** 不要先下结论。                                                                                                                |
| **③ 可操作性**     | 该能**展开看到每条探针的原始错误**（那是他判断的唯一依据）。<br>**不该**出现「代理有问题，去改配置」这类把结论替他下了的引导。                                   |
| **④ 判失败的反例** | · 显示成「代理正常」或「代理故障」（**把无法判定说成了某一侧**）<br>· 原始错误**展不开**（等于让他在没有依据的情况下判断）<br>· 给出一个指向代理设置的"修复"引导 |

## 9. 给审计者的三条通用要求

1. **读 `disabled`，不只读文本。**
   本批有两处改的就是可操作性（§5 的 GC 按钮、§1 与 §3 的"不给按钮"）。
   **纯文本扫描会把这两处都判成"通过"** —— 那正好漏掉本批唯一真正改变了用户能做什么的地方。

2. **每个动作都点一次，看落在哪儿。**
   「有按钮」和「按钮点了有用」是两件事。本轮删过「点得动、跳得走、就是到不了能修的那一页」的按钮。
   本文每一格都写了终点；**到不了那个终点 = 这一格失败**，与文案对不对无关。

3. **两种语言都看。**
   这批第三态**两份 locale 都加了词条**。
   ⚠️ 已知的一类历史缺陷是**英文界面上渲染出中文**（英文字段被写成了中文值）。
